# v2.6.0 · 暴击/爆伤软上限机制（计划）

> 目标：把暴击率钉死在 80% 软上限，超出部分 1:1 转化为爆伤；爆伤超过 320% 后增量效用只剩 10%（软膝）。
> 这是 `packages/core` 冻结层的机制改动，必须走「PRD → 分支 → `build:core --sync` → 发布说明 → 版本同步」流程。

## 一、用户已拍板的参数（原话）

> 「80%把，转化率1%：1%就行，爆伤320%以后增加只有之前的10%效果。」

| 项 | 规则 |
|----|------|
| 暴击软上限 | **80%**。超出 80% 的部分不再涨暴击率。 |
| 溢出转化 | 溢出按 **1 点暴击率 : 1 点爆伤** 转入 `critDmg`。 |
| 爆伤软膝 | `critDmg` 超过 **320%** 后，超出部分的增量效用只剩 **10%**（软膝，非硬墙）。 |

## 二、根因诊断

`packages/core` 现状（冻结）：

| 环节 | 文件/位置 | 现状 |
|------|-----------|------|
| 基础暴击 | `formulas.ts:24` | `crit = clamp(5 + agi*0.2, 0, 75)` |
| 装备加成 | `unit.ts:60` | `d.crit = clampE(d.crit, 0, 90)` |
| 性别（女） | `unit.ts:107` | `crit + 5`，`clampE(..., 0, 90)` |
| 坐骑 | `unit.ts:183` | `crit + critAdd*m`，`clampE(..., 0, 92)` |
| 遗物 | `unit.ts:183` 同类 | `crit + critAdd*m`，`clampE(..., 0, 92)` |
| 场地修正 | `battle.ts:188` | `u.derived.crit += w.critAdd`（建造后注入） |
| 爆伤基础 | `formulas.ts:25` | `critDmg = 150 + str*0.5 + int*0.5` |
| 爆伤追加 | 性别/遗物/特性/装备 | 直接加，无 320% 膝 |
| 战斗期爆伤 | `battle.ts:1152-1153` | `effCritDmg(u) = u.derived.critDmg + 10*lateDecay()` |

**问题**：暴击可被堆到 90~92%，无 80% 上限；爆伤无限线性增长、320% 后没有衰减。**用户要的是「暴击封顶、溢出喂爆伤、爆伤超 320% 软衰减」的构筑收敛。**

## 三、方案总览

新增单一归一化函数 `applyCritSoftCap(d: DerivedAttrs): DerivedAttrs`（置于 `unit.ts`），在**全链路派生组装完成、构造 Unit 之前**作为最终步骤调用。两处建造器都要包一层：

- `makeAlly`（`unit.ts:263-270`）：包在 `applyMount( applyTraitStatic( applyGrowthPct( applyGender( applyBody( applyEquipment( derive(primary), equipment ), bodyType ), gender ), hero.growthBonus ), hero.traitId ), hero.mount, hero.mountRarity )` 最外层。
- `makeEnemy`（`unit.ts:362`）：包在 `applyGender( applyBody( derive(primary), bodyType ), gender )` 外层（敌方通常到不了 80%，但保证规则全局一致、防御未来怪物暴击膨胀）。

### 3.1 函数实现（伪码）

```ts
// v2.6.0 暴击/爆伤软上限（用户需求）。纯派生数学变换，零 Math.random，回放逐 bit 一致。
export function applyCritSoftCap(d: DerivedAttrs): DerivedAttrs {
  const CRIT_CAP = 80;        // 暴击软上限
  const CDMG_KNEE = 320;      // 爆伤软膝阈值
  const CDMG_KNEE_EFF = 0.1;  // 软膝后增量效用
  const out: DerivedAttrs = { ...d };
  if (out.crit > CRIT_CAP) {
    const overflow = out.crit - CRIT_CAP;
    out.crit = CRIT_CAP;
    out.critDmg += overflow;  // 1 点暴击率 : 1 点爆伤
  }
  if (out.critDmg > CDMG_KNEE) {
    const over = out.critDmg - CDMG_KNEE;
    out.critDmg = CDMG_KNEE + over * CDMG_KNEE_EFF;
  }
  return out;
}
```

### 3.2 溢出保真（关键细节）

各阶段现有 `clampE(d.crit, 0, 90/92)` 会在软上限之前**截断**原始和 → 若先被 92 截断，溢出会少算 3 点（92−80 而非 95−80）。为保证「溢出 1:1」精确：

- 把 `unit.ts` 内装备/性别/坐骑/遗物的 crit 硬上限（90/92）改为**高护栏**（如 `clampE(..., 0, 200)`），仅作防爆 sanity 用；真正的 80% 封顶 + 溢出转化交由 `applyCritSoftCap` 统一裁决。
- 该护栏改动**不影响其他消费者**（crit 仅在 battle 经 `derived.crit` 命中判定使用）。

### 3.3 竞技场修正也必须过软上限

`battle.ts:188` 的 `u.derived.crit += w.critAdd` 是建造后按场地注入的环境修正，若不过软上限会让「虚空侵蚀 (+16%)」等场地突破 80%。方案：该处改为「加完再走一次 `applyCritSoftCap(u.derived)`」，使「暴击上限 80%」在英雄/敌方/场地三处全局一致。

### 3.4 与 lateDecay 的共存（设计分界）

`battle.ts:1152-1153` 的 `effCritDmg(u) = u.derived.critDmg + 10*lateDecay()` 是**层内 30s 后终局追赶的临时加成**，加在归一化之后的永久 `critDmg` 之上：

- 软膝（320%→10%）只压**构筑**溢出，不压**战局追赶**。两者职责清晰、互不冲突。
- 即：永久 `critDmg` 先过膝压缩；`lateDecay` 的临时 +10pp/s 再叠加其上（不二次过膝）。

## 四、确定性 & 门禁

| 项 | 说明 |
|----|------|
| 随机性 | 纯数学变换，零 `Math.random` → 回放逐 bit 一致。 |
| 触及 core | 是（冻结层）→ 必须开分支改 `packages/core`。 |
| parity | 改完必须 `build:core --sync`，保证 `packages/core` 与 `supabase/functions/_shared/core.js` 回放逐 bit 一致。 |
| guard / parity / smoke | 三道门重跑。注意：`crit` 最终值变化会改变战斗数值分布（预期内机制变更）；smoke 查的是**同版本内**确定性，应仍一致，但若 smoke 含跨版本基线比对需重对齐（确认方式：跑一遍看是否仍 bit 一致）。 |

## 五、影响与风险

- **战斗平衡变动（预期内）**：原堆到 90%+ 暴击的角色封顶 80%，多余转爆伤（高暴击率下爆伤放大更划算，DPS 更平滑收敛）。需跑模拟确认无退化（如某 build 爆伤被 320 软膝压到无收益）。
- **UI 面板**：`HeroPanel` 的 `crit`/`critDmg` 直接读 `derived`，会自动反映新值，无需改 UI 逻辑（仅数值变化）。
- **无新增随机流**：不新增 `rng()` 调用，不影响战斗走向序列。
