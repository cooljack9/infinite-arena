## 三、架构评估

### 3.1 结构（清晰，关注点分离到位）
```
src/
  game/        engine(战斗/公式/rng/缩放/单位) · content(数据驱动 21 个文件) · gen(遭遇/阵型/层生成) · state(zustand store)
  render/      ArenaCanvas · frame(渲染主循环) · sprites · sprite-templates
  screens/     6 屏 + intermission/(Hub + Equip/Forge/Shop + FilterBar/EqCard)
  audio/       AudioEngine · sfx
  dev/         preview(本地渲染验收页，已排除出产物)
```
- 56 文件 / 12,745 行，分层合理：`engine` 纯逻辑、`content` 纯数据、`render` 纯绘制、`screens` 纯 UI、`state` 单一数据源。
- 屏幕路由极简（`App.tsx` 按 `useGame(s=>s.screen)` 切换），无路由库依赖。

### 3.2 确定性设计（核心优势，也是稳定性根基）
- 逻辑时钟 20Hz 与渲染 60fps 解耦；`sim` 数学与 `render` 插值分离，渲染改动不影响确定性。
- `mulberry32` + `genLayer(layer, seed, mode)` 三元组可从种子完整复现层计划；伤害扰动走独立 `atkRng` 种子流，主序列零污染。

### 3.3 主要架构风险（巨文件）
| 文件 | 行数 | 风险 |
|------|------|------|
| `render/frame.ts` | 1748 | 渲染主循环 + VFX/fx 状态机集中，改动波及面大 |
| `game/engine/battle.ts` | 1531 | 战斗 tick / 结算 / AI 混于一处 |
| `game/state/store.ts` | 970 | 单一 zustand store 承载 ~30+ action，是最大可维护性瓶颈 |
| `render/sprite-templates.ts` | 727 | 美术模板数据量大，随英雄/Boss 增长会继续膨胀 |

> 这些文件「现在稳定」，但都是「改一处要想全局」的痛点；功能持续叠加时，store 与 frame 会先成为瓶颈。

## 四、技术栈评估

| 选型 | 评价 |
|------|------|
| React 18 + react-jsx | 仅用作 UI 外壳（菜单/休整/教学），战斗走 Canvas，分工正确，无过度依赖 |
| TypeScript（strict 开） | 类型安全到位；`noUnusedLocals/Parameters` 关闭（宽松，见「构建配置」） |
| Vite 5 | 构建快（706ms）、HMR 顺；`base` 动态兼容 GH Pages 子路径 |
| Canvas 2D | 对像素级特效（顿帧/震屏/太极光/岩浆）控制力强，优于 DOM/SVG |
| zustand | 轻量单一 store，学习成本低；但单 store 随规模需切片（见重构 P1） |

**结论**：技术栈与「纯前端确定性自动战斗」场景高度匹配，没有选型错配或过重依赖。

## 五、构建配置评估

- `vite.config.ts`：用 `base = process.env.BASE_PATH || (GITHUB_PAGES ? '/infinite-arena/' : '/')` 兼顾 CI 与本地；`rollupOptions.input` 仅 `index.html`，把 `preview.html`/`src/dev/` 排除出生产产物——正确。
- `tsconfig.json`：开 `strict`、`isolatedModules`、`noFallthroughCasesInSwitch`；`target ES2020`、`moduleResolution bundler`，配置现代。
- **minor 宽松项**：`noUnusedLocals` / `noUnusedParameters` 均为 `false`，死代码不会在编译期暴露。建议后续增量开启。

## 六、稳定性「观察点」（非当前缺陷，需长期守护）

1. **RNG 纪律是单点脆弱性**：确定性依赖「所有随机都走 seeded RNG」。任何新代码引入 `Math.random()` 或未登记种子流，都会悄悄破坏回放——需靠 code review 守护（现有 `atkRng` 独立流是正面范例）。
2. **store 单点**：所有经济结算集中在 `resolveRandomEvent` 等 action，已在 v2.9.4 堵住「越界层号刷金」「空包/没钱成交」两个经济漏洞；后续新增经济出口务必复用同一套「源与汇」校验。
3. **特征缺口（非稳定性）**：GDD §8.2 规划的「3 人联机」未实现，实为单人操控 3 英雄；与题面「三人进入竞技场」存在定位落差，但属产品范围问题，不影响稳定性。

## 七、重构优先级（按 影响 × 成本 排序）

### P1 — 高影响 / 中成本（建议近期做）
- **拆分 zustand store 为切片（slices）**：按领域拆 `meta`（localStorage 持久化）、`run/economy`（金币/背包/商店）、`battle`、`tutorial`、`inventory/equipment`。
  - 价值：降低认知负荷、减少合并冲突、提升单 action 可测性；为 v2.9.4 已验证的「经济源汇」校验提供独立单测锚点。
  - 风险：拆分会动到几乎所有 screen 的 selector，需配合 integration [19] 防回归。

### P2 — 中影响 / 中成本（按需做，触到再改）
- **`battle.ts` 分阶段抽取**：init / tick / resolution / AI 拆模块，单文件 1531 行降到可单测粒度。
- **`frame.ts` 的 VFX/fx 层外提**：把 fx 状态机（白热爆点/震屏/闪光分级）独立成 `render/fx/`，渲染主循环只负责调度。
- **引入标准测试框架（Vitest）**：当前 `scripts/*.ts` 自研脚本覆盖充分，但缺 watch/覆盖率/IDE 集成；Vitest 可与现有 esbuild 脚本并存迁移。

### P3 — 低影响 / 低成本（顺手做）
- 增量开启 `noUnusedLocals` / `noUnusedParameters`，逐步清死代码。
- `content/*.ts` 随英雄/Boss/装备增长继续膨胀时，按职业/品质再做二级拆分（当前 `equipment.ts` 480 行仍可控）。
- `sprite-templates.ts` 考虑数据外置（JSON/构建期生成），把「美术数据」与「渲染逻辑」彻底分开。

---

## 八、一句话总结

**架构选型正确、构建健康、运行时稳定（门禁全绿 + 确定性可复现），可以放心运行与继续迭代；唯一需要主动治理的是「状态层与渲染层巨文件」，优先级 P1 的 store 切片是 ROI 最高的下一步。**
