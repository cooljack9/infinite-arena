## 1. 目标与范围

### 1.1 目标

1. 一个**打开即玩**的网页游戏：3 人起队 → 进入无尽竞技场 → 自动战斗 → 结算 → 继续/重开。
2. 完全**静态**：所有逻辑在浏览器内运行，无需服务器（排行榜/存档用 `localStorage` 降级，生产再接后端）。
3. 一键部署到 GitHub Pages：开发仓 `push master` 触发 CI，构建后自动发布到公开仓 `cooljack9/infinite-arena` 的 Pages（详见 §11）。

### 1.2 技术约束（来自「静态 + 无后端」）

- **确定性模拟**：战斗用固定步长 + 种子随机，保证可复现（对应需求 4.4.6「种子锁定」思路）。
- **客户端唯一真相源**：运行态存内存 + `localStorage`。
- **性能上限**：深层 500+ 实体时仍可 60fps（需求 10 性能项），故战斗走 Canvas 而非 DOM。
- **子路径兼容**：GitHub Pages 以 `/<repo>/` 子路径提供，需配置 `base`。

### 1.3 Demo MVP 范围（明确的取舍）

| 模块 | MVP 包含 | 暂不做（二期） |
|---|---|---|
| 职业 | 4 大类 9 子类，**每类 1 名代表勇者**（共 9 名） | 每子类 2 名 |
| 属性 | 完整 4→7 转化公式（需求 5.3） | 皮肤/外观 |

## 2. 技术选型

### 2.1 前端框架：**Vite 5 + React 18 + TypeScript**

| 候选 | 结论 | 理由 |
|---|---|---|
| **Vite + React** ✅ | **采用** | 纯客户端 SPA，构建产物即静态文件；`base` 配置子路径简单；冷启动/HMR 快，适合 Demo 快速迭代 |
| Next.js | 备选 | 需求文档默认栈，但其静态导出（`output: export`）对 SPA 游戏收益低、子路径配置更繁琐；若未来要服务端排行榜再迁移 |

### 2.2 状态管理：**Zustand**

- 运行态（RunStore：当前层、队伍、遗物、阶段）与元进程（MetaStore：解锁、最佳层）分离。
- 理由：轻量、无 Provider 嵌套、便于战斗循环外读取。

### 2.3 渲染方案：**Canvas 2D（战斗）+ DOM/自定义 CSS（UI）**

- 战斗场景（单位、弹道、血条、伤害飘字）用单个 `<canvas>` + `requestAnimationFrame`。
- 菜单/HUD/结算用 React + 自定义 CSS 组件。
- 理由：500+ 实体下 DOM 必崩，Canvas 配合对象池可稳 60fps（需求 10）。

### 2.4 样式与组件

- **自定义 CSS**（`src/index.css` 内含游戏/UI 变量与组件样式），**不引入 Tailwind / shadcn / lucide**——Demo 阶段 UI 量小且高度定制（倍速滑块、渐变面板、受击抖动、辉光等），自写 CSS 比引入框架更可控、零额外依赖。
- UI 基础件（Button / Dialog / Card / Panel）按需求就地用 React + 自定义 class 实现，集中在各 `screens/` 与 `index.css`。
- 图标：战斗内用 Canvas 绘制职业符号（盾/剑/弓/法杖），UI 内用 Unicode 字符，不依赖图标库。

### 2.5 其它库

| 用途 | 库 |
|---|---|
| 种子随机 | 自写 `mulberry32`（小、确定性） |
| 动画 | 原生 rAF（战斗）/ `framer-motion`（UI 转场，可选） |
| 路径/部署 | `gh-pages` 或 GitHub Actions |

### 2.6 为什么不用后端

Demo 阶段全部本地：战斗确定性、存档 `localStorage`、分享卡用 canvas 截图。全球榜/联机留待生产（需求 8.2、5.9 服务端校验）。

## 5. 核心数据模型（TypeScript 接口）

### 5.1 属性（需求 5.3）

```ts
export interface PrimaryAttrs { con: number; str: number; agi: number; int: number; }

export interface DerivedAttrs {
  hp: number; pDmg: number; mDmg: number;
  atkSpeed: number;   // %
  dodge: number;      // %
  moveSpeed: number;  // %
  crit: number;       // %
  critDmg: number;    // %
  pResist?: number; mResist?: number; heal?: number;
}

export function derive(a: PrimaryAttrs, base: BaseValues): DerivedAttrs {
  return {
    hp:       base.hp + a.con * 10,
    pDmg:     base.pDmg + a.str * 2.0 + a.con * 0.3,
    mDmg:     base.mDmg + a.int * 2.0,
    atkSpeed: clamp(base.atkSpeed + a.agi * 0.4, 0, 200),
    dodge:    clamp(a.agi * 0.25, 0, 75),
    moveSpeed:clamp(base.moveSpeed + a.agi * 0.3, 0, 60),
    crit:     clamp(base.crit + a.agi * 0.2, 0, 75),
    critDmg:  150 + a.str * 0.5 + a.int * 0.5,
  };
}
```

## 6. 战斗引擎设计

### 6.1 固定步长模拟

- 逻辑频率 **20 tick/s**，渲染与逻辑解耦（累加器模式）。
- 每 tick：单位 AI → 移动 → 技能/CD → 结算伤害 → 产出事件。
- 确定性：所有随机走 `rng(seed)`，同 seed 同结果（需求 4.4.6）。

### 6.2 单位与 AI（需求 5.4）

```ts
export interface Unit {
  id: string; side: 'ally' | 'enemy'; pos: Vec2;
  primary: PrimaryAttrs; derived: DerivedAttrs;
  hp: number; maxHp: number; cd: number; skill: SkillDef;
  target?: Unit;
}
// AI：基于站位+威胁值选目标；玩家可「标记/嘲讽」覆盖
function think(u: Unit, allies: Unit[], enemies: Unit[]) { /* 选最近/最高威胁 */ }
function step(u: Unit, dt: number) {
  if (!u.target || dead(u.target)) u.target = acquire(u);
  moveToward(u, u.target.pos);
  u.cd -= dt;
  if (u.cd <= 0) { cast(u, u.target); u.cd = 1 / (u.derived.atkSpeed/100 + 1); }
}
```

### 6.6 三模式体系与个体差异化（v2.2）

**模式封顶常量**（`src/game/engine/scaling.ts`）：

```ts
export const NOVICE_CAP  = 5;    // 新手模式封顶（5 层有限教学战役）
export const ENDLESS_CAP = 500;  // 普通无尽 / 铁人无尽软上限（里程碑 100/200/300/400/500）
export function capFor(mode: GameMode): number {
  // 新手 = 有限战役；普通无尽 / 铁人无尽 = 深塔至 500 层
  return mode === 'novice' ? NOVICE_CAP : ENDLESS_CAP;
}
```

- `RunState.mode: 'novice' | 'normal' | 'ironman'`，`selectedMode` 是跨局玩家偏好（reset 不清除）。
- `finishBattle(win, layer, score)`：新手模式到达 `NOVICE_CAP(5)` 胜利 → 置 `endlessUnlocked=true`（持久化 `ia_endless`），**同时**解锁普通无尽与铁人无尽；`lastResult.mode` 记录本局模式。
- 普通无尽 / 铁人无尽未解锁时 `startRun` 强制回退新手（安全护栏）。
- 进度推进（BattleScreen.onEnd / PreBattle.skip）以 `capFor(run.mode)` 为封顶判据，不再硬编码 `DEMO_CAP`。
- **铁人无尽永久死亡（permadeath）**：`BattleSim.deadAllies` 记录本场阵亡友方 `heroUid`；`BattleScreen.onEnd` 在 `run.mode==='ironman'` 且胜利时调用 `store.removeDeadAllies(uids)` 永久移除该副本并把其穿戴装备卸回背包；普通无尽不调用（阵亡自动满血复活）。`removeDeadAllies` 守卫：团队 ≤1 或试图清空时直接 return，永远保留 ≥1 名。

#### 6.7.1 射程与站位教学（v2.4 需求 #3）
- 教学锚定 `PreBattle` 的 `id="tut-formation"`（「战前布阵」标题），选中队员后展示【射程圈】的语义说明。
- 文案要点：射程圈 = 该队员能打到的最远格数；射手/法师射程长可躲最后排输出，近战射程短须贴脸；坦克堵正面入口承伤、远程摆最后排对准敌人最前排，使射程圈覆盖最多目标。

**浮层**（`src/screens/TutorialOverlay.tsx`）：

- 美术规格见美术 §4.8。

### 6.8 容错机制（v2.4 需求 #5：允许失败 2 次）

玩家本局累计失败 **2 次内可重试同一层**，第 3 次失败才真正「游戏结束」。

- `RunState.failures`（`src/types.ts`）：本局已用掉的失败次数，初始 0；`startRun` 时归零。
- `store.setFailures(n)`：失败自增并写回 `run.failures`。
- `BattleScreen.onEnd` 失败分支：`failures = run.failures + 1`；若 `failures >= 3` 才 `finishBattle(false, layer, score)`（真正终结），否则 `setScreen('pre')` 退回同一层——因 `run.seed` 不变，**所见即所战、同层敌人完全一致**，玩家可在原布阵上修正重试。
- `PreBattle` 状态行显示「剩余容错：N 次」（`Math.max(0, 2 - failures)`），给玩家明确预期。
- `ResultScreen` 在 `!win && failures >= 3` 时打「已用完 2 次容错机会，本局终结」标签。
- **与铁人模式关系**：容错重试仅在同层重打，不触发 `removeDeadAllies`；铁人模式真正的永久死亡仍只在「胜利结算」时移除阵亡勇者（见 §6.6）。

## 7. 程序化关卡生成（需求 4.4.6）

```ts
export function genLayer(n: number, seed: number, mode?: GameMode): LayerPlan {
  const rng = mulberry32(seed + n);
  // 锚点层（强制固定）
  const isVacuum   = n % 10 === 0;           // 赛段末
  const isMutation = n % 10 === 0;           // 每10层
  // Boss 密度（v2.4 需求 #4）：每 3 关一个普通 Boss(colossal)，每 5 关一个强力 Boss(titan)
  const bossTier   = bossTierAt(n, mode);    // 'strong' | 'normal' | undefined
  // 原型抽取：禁止连续3层同原型（需读历史）
  const arena = pickArena(rng, lastArenas);  // A1/A3/A6
  // 若原布局无 Boss 台(B 块)但本层是 Boss 层，注入 2×2 Boss 台保证可打
  if (bossTier) ensureBossPlatform(arena);
  // 遭遇预算 = 玩家预期战力 × 亚线性缩放(6.1) × 连续赛段倍率(v2.4 平滑)
  const budget = expectedPower * enemyScale(n).hp * segmentMult(n);
  const waves = buildWaves(rng, budget, bossTier);
  return { layer:n, arena, waves, isVacuum, isMutation, bossTier, encounterBudget:budget };
}
```

> **v2.4 难度曲线优化（需求 #1）**：`segmentMult(n)` 旧版在 10/30/60 层用阶梯跳变（1 → 1.3 → 1.6 → 2），造成「过一层突然难一大截」的悬崖感（如 10→11 层敌人强度 +36%）。v2.4 改为随层深连续线性增长：`Math.min(1.9, 1 + 0.008 * max(0, n-1))`（每深 1 层 +0.8%，封顶 1.9）。与 `enemyScale` 的亚线性 √(n/20) 缩放叠加后整体平滑，玩家构筑收益持续有效，不再有突兀的难度台阶。
>
> **v2.4 Boss 密度（需求 #4）**：`bossTierAt(n, mode)` 每 5 关返回 `'strong'`（titan 体型，最霸气），每 3 关返回 `'normal'`（colossal 体型，压制感但非碾压）；新手模式（`mode==='novice'`）仅封顶层（`n >= NOVICE_CAP=5`）放一个普通 Boss 作收尾，保持入门温和。`buildWaves` 的 Boss 波从 `STRONG_BOSSES`（titan 池）/ `NORMAL_BOSSES`（colossal 池）抽取；普通波次逻辑不变。Boss 类新增 3 个 colossal 普通 Boss：角斗场守卫(物理坦克)/预言魔像(魔法坦克)/血色劫掠者(辟邪剑)。

生成后跑 **4.4.7 可读性清单** 自动校验（可达性/多样性/难度单调/战术冗余），不达标重 roll（限次）。

## 12. 性能与边界（需求 10）

- **对象池**：单位/飘字复用，避免 GC 抖动。
- **实体上限**：深层 500+ 实体时关闭命中特效细节、降低飘字频率。
- **伤害硬上限**：`Math.min(dmg, 2**31-1)`（需求 6.3），超限归零+硬直。
- **帧率**：锁定渲染帧率至刷新率 2/3，关闭超线程敏感逻辑（需求 10）。
- **确定性**：全随机走 `rng(seed)`，保证生成/战斗可复现。

## A.4 需求 4：锻造属性转移（Affix Transfer）

### A.4.1 类型扩展
```ts
export interface Affix {
  key: AffixKey;
  value: number;
  mode?: 'flat' | 'pct';   // 缺省视为 'flat'
}
```
生成规则：**`pct` 词条仅在橙、红品质装备上生成**；普通/蓝装只产 `flat`。

### A.4.2 转移规则
锻造界面选择 **目标装备（保留）** + **素材装备（销毁）**：

- 逐条尝试转移素材词条，单条成功率：
  `P = 0.35 + 0.10 × qualityLevel(素材)`
  其中 `qualityLevel`：normal=0 / blue=1 / orange=2 / red=3 → **35% / 45% / 55% / 65%**。
- **flat 词条**：同 `key` **数值累加**，不同 `key` **无限追加**（可叠任意条）。
- **pct 词条**：同 `key` **只保留一条**，取 `max(原值, 新值)`；不同 `key` 可各存一条。
- 目标装备**保留全部原有词条**（单向累积，不是重 roll）。
- 素材装备无论成功与否**一律销毁**；每层锻造次数沿用 `forgedThisLayer` 限制。
- 结算后返回「成功/失败」逐条日志，UI 以绿色/灰色列出。

## A.5 需求 5：装备合成与红装升星

### A.5.1 合成（Fuse）
| 素材 | 产物 |
|---|---|
| 2 件蓝装 | 1 件随机橙装（重新生成词条） |
| 2 件橙装 | 1 件随机红装（重新生成词条） |
| 红装 + 任意红装 | 目标红装 `star + 1`，素材销毁 |

- 合成不消耗金币，但**每层限 2 次**（`fusedThisLayer`）。

### A.5.2 红装星级
- `Equipment.star?: number`，红装默认 1 星，**上限 5 星**。
- 星级效果：**所有词条数值 × (1 + 0.25 × (star − 1))**
  → 1★ = 1.00×、2★ = 1.25×、3★ = 1.50×、4★ = 1.75×、**5★ = 2.00×**。
- 已满 5 星的红装不可再作为升星目标（UI 置灰）。
- 装备名称前缀显示星数：`★★★ 炽炎战铠`。

## A.6 需求 6：角色五星后属性突破

### A.6.1 类型扩展
```ts
export interface HeroDef {
  // ...
  star?: number;                       // 1 ~ 5
  bonusPct?: Partial<PrimaryAttrs>;    // 突破累积的百分比加成，无上限
}
```

### A.6.2 购买/招募逻辑
```
购买同名角色：
  ├─ 队伍中没有 → 以 1★ 加入队伍
  ├─ 已有且 star < 5 → star += 1
  └─ 已有且 star == 5 → 随机一项一级属性 bonusPct[k] += rand(3, 5)
```
- 随机范围 **3%~5%**（整数或一位小数，取 `3 + rng()*2`，保留 1 位小数）。
- 突破**无次数上限**，是金币的长期出口。
- `primaryAtLevel()` 计算顺序：
  `基础值 → × starMult(star) → + starGrowthBonus → × (1 + bonusPct[k]/100)`。
- 面板中突破部分以 `+12.4%` 形式独立高亮显示。

### 12.9 v3.1 新需求实现（六项修复：必爆判定 / 升星强化技能 / 生成物编号 / 个体姓名 / 部署页可视化 / 性格索敌）

> 对应本迭代 6 项用户反馈。`npm run verify` 四道闸门全绿；`smoke.ts` 新增 `[5] v3.1 六项修复` 受控探针组，逐条把「需求描述」钉成可回归的数值断言（不再靠日志关键字匹配——正是关键字匹配掩盖了 §12.9.1 这个 bug）。

#### 12.9.1 贯日神射：修「伤害翻倍」为「必定暴击」（需求 #1）

- **问题**：`battle.ts::castSkill` 的 `deadshot` 分支对 `hp > 50%` 的目标同时给了 **×2 伤害**（`pDmg*4 + pDmg*4`）**和** `exec || full` 的强制暴击，实际结算是 `400% × 2 × 暴伤`。而 `SKILLS.deadshot.desc` 与 `SKILL_STAGE2.deadshot` 两处文案都只写了「必暴」，数值与描述长期对不上。
- **修复**：伤害恒为 `pDmg × 4 × P`（`P` = 星级乘子，见 §12.9.2），高血量目标只吃「必定暴击」这一条布尔量。血线抽成常量 `STAGE2_CFG.deadshotCritHpGate = 0.50`（原先「满血 `hp >= maxHp - 0.5`」与「>50% 翻倍」两条门槛并存，现在统一为一条）。
- **文案同步**：`skills.ts` 描述改为「9 格内单体 400%物伤，蓄力贯日一击」；`traits.ts` 的二段说明改为「目标生命高于 50% 时，本次射击必定暴击（伤害倍率不变）」。
- **回归**：`smoke [5]①` 用受控探针——冻结 `crit=0`、`cd=1e9`、木桩 `scaleDmg=0`，分别在目标 100% / 45% 血量下取**第一条伤害飘字**，比值必须等于 `critMult`（暴伤系数）而**不是** `2×critMult`。实测 `501 / 256 = 1.957 ≈ critMult 1.955`。

#### 12.9.2 升星真正强化签名技（需求 #2）

- **问题**：升星只走 `starMult` 放大一级属性，签名技的倍率全部写死在 `battle.ts` 里，1★ 与 5★ 的大招数值完全一致——玩家的直观感受就是「技能一开始就满级」。
- **数值模型**（`classes.ts` 新增）：
  - `skillLevelOf(star) = clamp(1, 5, round(star))`——技能等级**就是**星级，不引入第二条养成线；
  - `skillPowerMult(star) = 1 + 0.18 × (level − 1)`——效果 **+18%/星**，刻意复用 `starMult` 的 0.18，让升星只有一条收益斜率；
  - `skillStarCdr(star) = 0.04 × (level − 1)`——冷却 **−4%/星**（5★ −16%）。
- **接线**：
  - `unit.ts::makeAlly` 写入 `Unit.skillPower = skillPowerMult(star)`；星级 CDR 与专属红装 CDR **先相加再统一封顶 55%**（`Math.min(0.55, skillCdr + skillStarCdr(star))`）——分别封顶会让「5★ 角色 + 5★ 专属红装」拿到 45% + 16% = 61%，大招循环快到能盖住整局节奏。
  - `battle.ts::castSkill` 开头取 `const P = this.skillPow(u)`，9 个 case 的效果量逐一乘 `P`（嘲讽震荡波 / 符甲护盾 / 偃月突斩含势能吸血 / 无形剑罡 / 神火霹雳 / 贯日神射 / 太极封禁 / 青藤回春），召唤物在 `makeSummon` 里**攻击与生命同乘 `P`**（只抬攻击会让召唤流 5★ 仍是一碰就碎的纸人，读不到升星收益）。
  - `skillPow` 刻意不塞进 `dealSkill`：`dealSkill` 同时服务坐骑技与元素附伤，塞进去会让坐骑吃**两层**星级乘区。
- **回归**：`smoke [5]②` 必须把「属性成长」与「技能强化」拆开才有意义——同一探针在 1★/5★ 下的原始伤害比 `3.980` 里同时含 `pDmg` 增长；先算 `atkGain = star5.derived.pDmg / star1.derived.pDmg = 2.312`，再取 `skillGain = 3.980 / 2.312 = 1.722`，断言其等于 `skillPowerMult(5) = 1.72`。

#### 12.9.3 场内生成物编号唯一（需求 #3）

- **问题**：召唤物 id 为 `'sum' + Math.floor(time*1000) + kind`、Boss 分身 id 为 `clone{time*1000}_{idx}`。同一 tick 内两名召唤师同时产出同类型召唤物（或「军团」特性一次补两只）会得到**完全相同的 id**。而 id 是 `targetId` / `damagers` / `pathCache` / 渲染 key 的主键，撞号会导致索敌串目标、寻路缓存互相污染、渲染插值跳变等一连串隐性 bug。
- **修复**：`BattleSim` 增加实例级单调计数器 `spawnSeq` 与 `nextSpawnId(prefix)`，召唤物与 Boss 分身**共用同一条序列**（`sum_{kind}_{n}` / `clone_{idx}_{n}`）。计数器挂在 sim 实例而非模块级：同 seed 同回放必然同序列，又不会被「玩家开过几次编队界面」这类外部调用次数污染。
- **回归**：`smoke [5]③` 用 3 名造物术师 × 8 个种子跑满层（含 Boss 层），逐 tick 断言 `new Set(ids).size === ids.length`，并统计非 `u` 前缀的生成物 id 数。实测 32 个生成物、0 次撞号。

#### 12.9.4 个体随机姓名（需求 #4）

- **问题**：旧显示名 = 职业称号 + 罗马数字（`铁壁镇守 II / III`）。这套编号在部署页、战报、装备列表里到处出现，把三个属性/体型/性别都不同的角色写成了「同一个人的三份拷贝」，与 `variant.ts` 的个体化设计互相拆台。
- **新增 `content/names.ts`**：`randomHeroName(seed, gender, takenNames)`——姓取百家姓 100 个，名按性别分池取字、1~2 字随机；完全由种子驱动（同 seed 同名），支持传入「已占用姓名」集合做同队去重。
- **接线**：
  - `types.ts`：`HeroDef.personalName`；`dupIndex` 保留但不再驱动显示名（仅内部统计 / 存档兼容）；`Unit.title` 承载职业称号。
  - `unit.ts::displayName(hero)` 由 `(name, dupIndex)` 改为 `hero.personalName || hero.name`，**不再追加任何后缀**；`makeAlly` 同时写 `name`（姓名）与 `title`（称号）。
  - `variant.ts::variateHero(base, seed, takenNames)`：**已有姓名的副本不重摇**——玩家认识的是「孙澜」，不是「第 3 号铁壁镇守」，中途改名等于抹掉这份记忆。
  - `run.ts::startRun` 逐个生成并累积 `takenNames`，开局三人不撞名；`economy.ts::recruit` 把队内已用姓名传入去重。
- **回归**：`smoke [5]④` 生成 12 个副本，断言：`personalName` 均已设置 / 显示名无 `II`、`III`、数字后缀 / 12 名互不重复 / 同 seed 复现同名 / 预置 `personalName` 时不被覆盖。

#### 12.9.5 部署页：危险地形 + 职业剪影棋子（需求 #5）

- **棋子重做**：旧棋子是「纯色圆 + 1 个字」。新增 `HeroToken` 组件——用战斗同源的 `drawSprite(ctx, subclass, ...)` 在离屏 canvas 上画**职业专属像素剪影**（含 `bodyType` / `gender` / `star`，与实战外观一致），底色为职业色低透明（`info.color + '2e'`）、边框为职业色，底部压一条**姓名条**。`CELL` 由 22 → **26**（22px 塞不下可读姓名；26px 是「名字看得清」与「20 列不炸屏」的折中），画布高出格子 8px 并上溢，给 2★+ 的头顶星级留净空。

#### 12.9.6 性格系统（索敌偏好，需求 #6）

- **新增 `content/personalities.ts`**：6 种性格（纯数据 + 纯函数，无随机、无副作用）——

  | id | 中文 | 偏好 | 权重 |
  |---|---|---|---|
  | `valiant` | 不畏强暴 | 生命 > 80% 的敌人 | 1 |
  | `hunter` | 猎手 | 当前生命百分比最低者 | 1 |
  | `breaker` | 攻坚者 | 敌方前排 | 1 |
  | `assassin` | 专业刺客 | 敌方后排 | 1 |
  | `savior` | 救困扶危 | 战力评分最高者 | 1 |
  | `steady` | 随遇而安 | 就近（= v3.0 默认行为） | 1.6 |

  `steady` 权重调高到 1.6，避免全队都是极端个性。`rollPersonality(r)` 为加权抽取，随机数由调用方（`variateHero`）传入，确定性不被破坏。
- **设计约束**：性格**只影响索敌，不给任何数值加成**——它是风味与战术变量，不是第三条养成线，否则玩家会去刷性格而不是玩阵容。
- **索敌实现**（`battle.ts::acquireTarget` → `byPersonality`）：
  - 优先级：**嘲讽 > 性格 > 默认**。`pool` 已被 `tauntUntil` 过滤，性格只在「允许选谁」的范围内挑；控制效果必须能压过个性，否则前排的存在意义被削掉一半。
  - **不做纯优先级，做「偏好分 × PREF_W − 距离」的加权**（`PREF_W = 6`，即偏好满分 ≈ 值得多走 6 格）。纯优先级会让近战刺客无视贴脸坦克、横穿整张图去够后排法师，路上被围殴致死——玩家看到的不是「性格」，是「AI 犯蠢」。
  - **「前排/后排」以我方阵型重心为基准**（排除召唤物），而不是攻击者自身位置：用自身位置的话「前排」会退化成「离我最近」，攻坚者与随遇而安就没区别了。阵深归一化到 `front ∈ [0,1]`（1=最前）。
  - 战力评分 `threat(f) = pDmg + mDmg + maxHp × 0.04`，归一化后供 `savior` 使用，Boss 天然分高。
  - `steady` 直接短路，不进偏好通道，保持 v3.0 行为逐位一致。
- **生成**：`variateHero` 在**属性摇完之后**才取 `rng()` 摇性格，保证「旧存档 + 同 seed」的 `basePrimary / bodyType / gender` 与 v3.0 逐位一致，只在末尾多消费一个随机数——回放兼容优先于代码美观。已有性格不重摇。
- **回归**：`smoke [5]⑤` 用 5 组受控场景（各含「满血中距 / 残血中距 / 敌前排 / 敌后排 / 远处 Boss」诱饵），跑 1 tick 后读 `targetId`，断言 5 种性格各自选中预期目标；另用 5 个 `steady` 对照组验证「全部选最近」；再跑 3000 次 `rollPersonality` 验证 6 种全部出现，以及同 seed 确定性、预置性格不被覆盖。
