# 无限勇者竞技场 · 前后端分离架构总览

> 版本：v4.0-arch · 基线代码：v3.1.0 (d9c55bc)
> 目标：**后端权威计算，前端只渲染**；同一份后端代码既能跑在 Supabase，也能作为本地库直接调用（双通路）。

---

## 0. 一句话结论（先说最重要的）

**本项目的战斗引擎已经是 bit 级确定性的**（跑通 PoC 实测：**80 场战斗 checksum 全等**，
且在 **5 个 JS 运行时**上逐 bit 一致，见 §3 与 §4 P0-5）。
所以：**后端不需要下发逐帧战斗数据，只需下发 `battleSeed + 双方开局快照 + 结果校验和`，前端本地跑同一份引擎即可完全复现。**

PoC 实测（`scripts/backend-poc.ts`，normal 模式，逐层采样）：

| 层 | 单位数 | 逐 tick 事件流 | replay 回放包 | 压缩比 |
|---|---|---|---|---|
| 1 | 5 | 24.6 KB | 5.5 KB | 4.5× |
| 2 | 5 | 53.9 KB | 5.6 KB | 9.6× |
| 3 | 6 | 125.6 KB | 6.6 KB | **19.0×** |
| 4 | 5 | 75.6 KB | 5.7 KB | 13.3× |
| — | — | — | — | **整体 13.9×** |

> ⚠️ 修订说明：本文早期版本写的是「0.14 KB / 783×」，那是只算了 `seed + checksum`、
> **漏算了开局快照**得出的数字，属于虚报。真实 replay 包必须携带双方单位的完整开局
> 状态（见 §4 的深拷贝教训），单场 5.5–6.6 KB。以实测为准。

关键在于**增长曲线的形状**，而不是某个瞬时倍数：
- replay 包只随**单位数**增长（O(units)），且完全不随战斗时长变化
- 事件流随**单位数 × tick 数**增长（O(units × ticks)）

所以层数越高、战斗越久，差距越大——第 3 层 6 个单位打满就已经 19×，而 replay 还是 6.6 KB。

这不是省流量的小优化，而是决定架构形态的关键：
- 前端能**任意倍速、暂停、拖拽进度条**（本地有完整引擎，不受网络约束）
- 后端单场结算 **3.8–14.6ms**（低层/高层，PoC 实测均值），Edge Function 成本可忽略
- 天然支持**断线重连**（只要 replay 包还在，本地能重放整场）

## 1. 为什么这个项目特别适合做前后端分离

分层现状（读代码得出，不是文档抄的）：

```
src/game/engine/     纯 TS，零 React、零 DOM、零 Math.random  ← 可整体搬到后端
src/game/content/    纯数据表 + 纯函数                        ← 可整体搬到后端
src/game/gen/        关卡生成，纯函数 + 种子                   ← 可整体搬到后端
src/game/state/      zustand store（含 4 处 Math.random 兜底）  ← 拆分：规则搬后端，视图留前端
src/render/          Canvas 渲染                              ← 留前端
src/screens/         React UI                                 ← 留前端
```

`engine + content + gen` 三层**已经是 headless-safe 的**，封测报告用它跑过 10,080 场无崩溃。这三层就是天然的"后端内核"，几乎零改造即可复用。

**切分面选择：按 `BattleSim` + `store slices` 切，不按屏幕切。**
理由：屏幕是表现，会变；规则是资产，稳定。按屏幕切会导致同一条规则散落在多个接口里。

## 2. 双通路架构（本地 / 服务器）

核心是一个 **`GameBackend` 接口**，两套实现，前端只依赖接口不依赖实现：

```
                    ┌─────────────────────────────┐
                    │      前端（渲染 + 特效）      │
                    │  React / Canvas / Audio      │
                    └──────────────┬──────────────┘
                                   │  只调用 GameBackend 接口
                    ┌──────────────▼──────────────┐
                    │   GameBackend（TS interface）│
                    └───────┬─────────────┬────────┘
                            │             │
              ┌─────────────▼──┐      ┌───▼──────────────────┐
              │ LocalBackend   │      │ RemoteBackend        │
              │ 同进程直接调用  │      │ HTTP → Supabase      │
              │ 单机/离线/测试  │      │ Edge Functions       │
              └────────┬───────┘      └───┬──────────────────┘
                       │                  │
                       └────────┬─────────┘
                                │  共享同一份代码
                    ┌───────────▼────────────┐
                    │   @arena/core（核心包） │
                    │  engine + content + gen │
                    │  + rules（经济/商店/升星）│
                    └────────────────────────┘
```

**关键纪律：`@arena/core` 是唯一真理来源。** 两条通路调用的是**同一个函数**，不是"两份看起来一样的实现"。
后者是经典陷阱：本地和线上算出不同结果，且只在生产环境暴露。

### 通路切换

```ts
// 一行切换，其余代码零改动
const backend: GameBackend =
  import.meta.env.VITE_BACKEND === 'remote'
    ? new RemoteBackend({ url, anonKey })
    : new LocalBackend({ storage: localStorage });
```

三种运行形态：

| 形态 | 后端实现 | 数据落点 | 用途 |
|---|---|---|---|
| **单机模式** | LocalBackend | localStorage / IndexedDB | 离线玩、GitHub Pages 静态部署 |
| **联机模式** | RemoteBackend | Supabase Postgres | 排行榜、防作弊、跨端同步 |
| **测试模式** | LocalBackend | 内存 | 单测 / 封测流水线（10,080 场） |

## 3. 确定性实测报告（本次亲自验证，非引用文档）

写了独立探针 `determinism_probe.ts`，完整复刻 `BattleScreen` 的真实建 sim 路径（`genLayer → variateHero → makeAlly/makeEnemy → sanitizeFormation → BattleSim`），逐 tick 抓取全场指纹（位置/血量/护盾/CD/索敌目标/控制状态/特效数），共 5 组 seed × layer 组合。

### 结论：物理层 bit 级确定，但**单位 id 不确定**

首轮 **8/12 FAIL，全部在 tick=0 分歧，但胜负与总 tick 数完全一致** —— 这个signature说明分歧不在物理演算，而在标识符。

定位到三个**模块级计数器**：

| 文件 | 代码 | 问题 |
|---|---|---|
| `src/game/engine/unit.ts:16` | `let uid = 0; nextId = () => \`u${uid++}\`` | 跨 sim 实例累加 |
| `src/game/engine/battle/common.ts:20` | `let bId = 0; nextBuildingId = () => \`b${bId++}\`` | 同上 |
| `src/game/state/slices/helpers.ts:113` | `let heroUidSeq = 0; nextHeroUid()` | 同上 |

把 id 按首次出现顺序归一化后重跑：**12/12 ALL PASS**，包括交错执行（两个 sim 并行 tick 互不污染）。

> 讽刺的是 `common.ts:17-19` 的注释明确写了"不复用 unit.ts 的 nextId()，否则 id 会取决于玩家之前打开过几次编队界面，破坏回放一致性"——作者意识到了这个风险，但自己的 `bId` 犯了同样的错。`battle.ts` 里的 `spawnSeq` 则做对了（挂实例）。

### 为什么这在单机无害，但在前后端分离下是 P0

单机时 id 只是内部主键，玩家看不见，胜负也不受影响。
但服务器化后：
- **服务端算出的 `u3` ≠ 客户端算出的 `u7`** → 校验和对不上 → 权威校验全部误报
- 事件流里的 `targetId` / `damagers` 归因表全部错位
- 断线重连后 id 重新编号，回放串目标

**必须修**（方案见 §4，改动约 20 行）。

### 校验和可用作防作弊锚点

探针 [D] 组验证：改 seed / 改层数 / 改阵容，三者都会让 trace 校验和改变。
→ 服务端可只存 `checksum`，客户端上报结果时比对，篡改任一输入都会被发现。

### 3.5 端到端复现验证（`scripts/backend-poc.ts`）

探针只证明了"同一份代码跑两次一样"。真正要证的是**"后端算的，前端能一模一样地放出来"**——
这是整个架构的承重墙，所以单独写了 PoC 走完整通路：

```
后端 rules.runBattle  →  replay 包（JSON 序列化）  →  前端 rules.replayBattle  →  比对 checksum
```

实测结果：

| 项 | 结果 |
|---|---|
| 样本 | 10 局 / **80 场战斗**（novice + normal，1–15 层，胜率 69%） |
| tick 数全等 | **80 / 80** |
| checksum bit 级全等 | **80 / 80** |
| 同种子跨后端实例 | **一致**（可复现 = 可申诉、可回放、可反作弊） |
| 同种子**跨运行时** | **一致**（Node / Deno / Chromium / Firefox / WebKit，见 §4 P0-5） |
| 后端结算耗时 | 均值 **12.22ms/场**（新手短局 3.3ms，无尽深层 307 tick 约 15.2ms） |

跑法：

```bash
npm run backend      # 等价于下面这条
npx esbuild scripts/backend-poc.ts --bundle --platform=node --format=esm \
  --outfile=node_modules/.cache/poc.mjs && node node_modules/.cache/poc.mjs
```

### 3.6 PoC 中真实翻的两次车（比"全绿"更值得记）

**① 快照字段白名单 → 前端复现漂移 168 vs 144 tick**

第一版 `UnitSnapshot` 是手写的字段白名单。结果漏了 7 个字段，其中致命的是：

| 字段 | 开局真值 | 白名单版本填的 | 后果 |
|---|---|---|---|
| `skillCd` | `0`（技能就绪） | `skill.cd`（要等满 CD） | 全场技能节奏错位 |
| `dmgMult` | `1.06`（遗物加成） | 写死 `1` | 伤害偏低 |
| `combo` / `heavyBurst` | `3` / `1~2` | 写死 `0` | 重击节奏错位 |
| `traitStacks` / `traitTimer` / `dupIndex` | 非 0 | 漏 | 特性行为偏移 |

**最危险的地方在于：胜负还是 win，肉眼完全看不出来。** 只有 checksum 抓得住。

白名单的问题不是"这次漏了"，而是**引擎每加一个字段就会再漏一次，且静默**。
最终改为：`UnitSnapshot = Unit` 的**全量深拷贝**。代价是单位快照 ~0.6 KB，换来的是
"快照随 Unit 定义自动演进"。

**② 引用共享 → tick 前抓的快照被战斗改写**

诊断发现 **5/5 单位的 `derived` 对象在战斗中被就地 mutate**。
快照虽然在 tick 之前抓，但 `primary/derived/skill` 是**引用**，而 JSON 序列化发生在
战斗结束之后——前端拿到的其实是"战斗结束态"冒充"开局态"。

深拷贝顺带解决了这个问题。并且刻意选 **JSON round-trip 而非 `structuredClone`**：

> 远程通路必然经过 JSON 序列化（`undefined` 字段会消失）。本地通路若用
> `structuredClone` 保留 `undefined`，就会出现**"本地测全过、上线就漂"**的经典事故。
> 主动把传输损耗前置到本地，两条通路才真正同构。

## 4. 必须先做的改造（P0，共 5 处）

### P0-1：模块级计数器改为实例级 —— 🟡 已落过渡方案

PoC 里这个问题**真的翻车了**：`同种子跨后端实例结果一致` 一开始是 FAIL。
原因正是模块级计数器——`be2` 虽是新后端实例，但 `uid` 是**进程级**的，早被
`be` 跑过的 50 场推到了 250+，于是同一个 seed 在两边生成 `u0..` 和 `u250..`，
checksum 直接漂。**这坐实了它是 P0 而不是洁癖。**

已实施的过渡方案（改动 6 行，PoC 复测通过）：

```ts
// src/game/engine/unit.ts
export const resetUid = (n = 0) => { uid = n; };
// src/game/engine/battle/common.ts
export const resetBuildingId = (n = 0) => { bId = n; };
```

调用点收敛到 core 内部，**前后端都不许自己写**：

```ts
// src/backend/rules.ts
export function buildUnits(...) { resetUid(0); /* ... */ }
export function makeSim(i: SimInput) {           // ← 前后端唯一的装配入口
  const sim = new BattleSim([...i.allies, ...i.enemies], i.arena, i.battleSeed);
  sim.setBuildingScale(i.buildingScale.hp, i.buildingScale.dmg);
  if (i.buildings.length) { resetBuildingId(0); sim.spawnBuildings(...); }
  return sim;
}
```

> 装配顺序本身就是协议的一部分（建筑计数器要在 `spawnBuildings` 之前归零）。
> 任何一边自己手写这段顺序，都会在某次重构后悄悄错位，而错位的表现是
> **"胜负一样、过程不同"**——肉眼不可见。所以必须只留一个入口。

安全性：JS 单线程内"重置 → 构建 → 开打"是一段不可中断的同步代码，
Node / Deno Edge Function 均成立。

**仍需在阶段 1 做的终态**（抽 `@arena/core` 时）：改为注入式 `IdGen`，
彻底消灭模块级可变状态——过渡方案挡不住"将来有人在构建中间插入 await"。

```ts
export interface IdGen { next(prefix: string): string }
export class SeqIdGen implements IdGen {
  private n = 0;
  next(prefix: string) { return `${prefix}${this.n++}`; }
}
export function makeAlly(h: HeroDef, lvl: number, eqs: Equipment[], opt?: {...}, idGen?: IdGen)
```

`nextHeroUid` 特殊些：它是**跨战斗持久**的队伍成员 id。服务器化后应改为**后端分配**（数据库自增或 uuid），前端不再自己生成。PoC 里 `LocalBackend.startRun` 已改为固定 `H1/H2/H3`，不再走模块计数器。

### P0-2：清除 store 里的 `Math.random`

| 位置 | 现状 | 改造 |
|---|---|---|
| `run.ts:30` | `startRun` 用 `Math.random()` 生成 run seed | 后端分配 seed（`crypto.randomUUID` 派生或 DB 序列） |
| `run.ts:180` | MVP 奖励属性 `Math.random()` 选 key | 改为 `mulberry32(seed ^ layer ^ hashStr(mvpUid))` |
| `economy.ts:184/208/249/267` | 无 run 时的兜底 | 后端化后 run 必然存在，直接抛错而非静默随机 |

`run.ts:180` 是**真实的确定性漏洞**（不是兜底路径）——同一场战斗重放，MVP 奖励属性会变。

### P0-3：种子派生必须显式传参

现状多处种子掺入 `tradeCount` / `refreshCount` / `inventory.length`：

```ts
seed = run.seed ^ (layer*2654435761) ^ (tradeCount*40503) ^ (inventory.length*2246822519)
```

这在单机能工作（状态就在本地），但服务器化后**这些值必须随请求显式上报并由服务端校验**，否则：
- 客户端谎报 `tradeCount` → 刷出更好的商店
- 服务端与客户端的 `inventory.length` 不同步 → 结果分歧

**改造原则：服务端只信自己数据库里的值，请求里的同类字段一律忽略。**

PoC 里已顺手堵上一个相关漏洞：`StartRunReq.debugSeed` **只在 LocalBackend 生效**。

```ts
/** RemoteBackend 必须无条件忽略本字段：种子是整局所有掉落/Boss/商店的母体，
 *  允许客户端指定 = 允许玩家枚举种子挑一个必出神装的开局，排行榜当场作废。 */
debugSeed?: number;
```

### P0-4：快照必须全量深拷贝（PoC 新增）

见 §3.6 ①②。一句话：**`UnitSnapshot = Unit` 全量深拷贝，禁止字段白名单，禁止前端"重建"逻辑。**

落地约束（已在 `rules.ts` 实施）：

| 约束 | 实现 | 违反后果 |
|---|---|---|
| 快照全量 | `JSON.parse(JSON.stringify(u))` | 漏字段 → 静默漂移，胜负还一样 |
| 切断引用 | 同上（深拷贝） | `derived` 被战斗改写 → 快照失真 |
| 模拟传输损耗 | 用 JSON 而非 `structuredClone` | 本地全过、上线就漂 |
| 前端不重建 | 只调 `rules.replayBattle` | 两套重建逻辑必然分叉 |

### P0-5：演算路径禁用"规范只要求近似"的 Math 函数 —— ✅ 已完成

**这条是整个 P0 清单里代价最大、也最不直观的一条**，完整推导见
[07_跨引擎浮点一致性.md](./07_跨引擎浮点一致性.md)。摘要：

ECMA-262 把 `Math` 分两档。`+−×÷` 与 `Math.sqrt` 被 IEEE 754 要求**正确舍入**，
跨实现逐 bit 一致；而 `sin / cos / atan2 / hypot / exp / log / pow / cbrt`（以及 `**` 运算符）
是 *implementation-approximated*，**规范明确允许各实现给出不同结果**。

实测 2 万点/函数、五个运行时：

- `Math.sin` / `Math.cos` 各有 **4 种不同实现**（V8 12.4 / V8 15.0 / SpiderMonkey / JSC）
- **V8 12.4 与 V8 15.0 在 6 个函数上不同** —— 同一引擎、隔三个大版本就漂
- `Math.sqrt` 是唯一全场一致的

第三条最要命：它意味着 **Supabase 例行升级 Edge Runtime，就能让全体玩家的本地回放
静默对不上**，而服务端自己算得好好的，没有任何报警。

改造（已完成）：

| 措施 | 位置 |
|---|---|
| 新建确定性数学库 `dsin/dcos/dpow/dpowi/drot` | `src/game/engine/detmath.ts` |
| `dist()`/`len2d()` 用 `sqrt(dx²+dy²)` 替代 `hypot` | `battle/common.ts`（覆盖 13 处调用点） |
| Boss 分身坐标、守卫铺位坐标、龙息锥形张角 | `battle.ts` |
| 敌人 HP/伤害缩放 `Math.pow` → `dpow` | `scaling.ts`（**第二轮才发现的漏网之鱼**） |
| 主题褪色 `Math.pow` → `dpowi` | `arenas.ts` |
| 静态闸门，命中即 exit 1 | `npm run guard`（已并入 `verify`） |

验证：五个运行时（Node 22 / Deno 2.9 / Chromium 151 / Firefox 153 / WebKit 26.5）
跑 18 场基准战斗，**36 个 checksum 逐 bit 全等**。性能代价 0.01%。

**代价：一次性基准位移。** `dsin/dcos` 与原生在约 25% 的输入上差 1 ULP，
足以改变战斗走向，因此 `CORE_VERSION` 已从 `4.0.0-poc` 升到 `4.1.0-detmath`
（旧回放不兼容）。往后不会再位移——detmath 的输出不再依赖宿主引擎。

> 两条可迁移的经验：
> 1. **`Math.pow` 比三角函数更容易漏。** 第一轮排查只盯着 `sin/cos/atan2/hypot`，
>    而 `scaling.ts` 里那个 `Math.pow(n/k, 0.5)` 直接决定每层敌人的血量。
>    靠人眼逐个找一定会漏，所以必须上静态闸门。
> 2. **验证浮点一致性必须做大规模扫描。** 手挑的 7 个探针值在三个浏览器上全部 PASS，
>    差点得出"Firefox 没问题"的错误结论；换成 2 万点采样后立刻分道扬镳。

## 5. 倒计时驱动的请求时序（本次核心需求）

你要求的两处倒计时，本质是**用倒计时的时间窗口掩盖网络延迟**——这是正确的做法。

### 5.1 战斗：5 秒倒计时

```
t=0.0s   玩家点「开战」
         ├─→ 前端：立即启动 5s 倒计时动画（本地，不等网络）
         └─→ 后端：POST /battle/start  { runId, layer, formation, clientNonce }
t~0.3s   后端返回 { battleId, seed, snapshot, checksum, result, rewards }
         └─→ 前端：静默预载，前端本地跑一遍 sim 校验 checksum
t=5.0s   倒计时结束 → 弹出「开战」→ 播放战斗
```

**关键设计**：
- 倒计时是**前端本地**跑的，不依赖网络。网络在这 5 秒里悄悄完成。
- 后端返回的 `result` 是**权威结果**；前端本地复现只是为了"播出来"，不是为了"算胜负"。
- 若 5 秒内网络未返回：进入「连接中」状态并允许重试；**绝不用本地结果冒充权威结果**。
- 若本地复现的 checksum ≠ 后端 checksum：**只上报遥测，不打断玩家、不判作弊**。
  照常播放后端下发的 `outcome`。理由见 07 §6——无法排除"某个未知运行时的浮点实现差异"
  这一无辜解释，据此惩罚等于让用户为环境差异背锅。

### 5.2 商店操作：3 秒倒计时

商店购买 / 升星 / 刷新等，走 **乐观 UI + 3 秒确认窗**：

```
t=0.0s   玩家点「购买」
         ├─→ 前端：立即乐观更新 UI（金币扣除、物品入包），显示 "购买中 3…2…1"
         └─→ 后端：POST /shop/buy { runId, itemId, idempotencyKey }
t~0.2s   后端返回权威状态 { gold, inventory, ... }
t=3.0s   倒计时结束 → 用权威状态**覆盖**乐观状态
         若后端拒绝（金币不足/物品已售）→ 回滚 + 明确错误文案
```

**为什么是覆盖而非合并**：合并会产生"客户端认为有、服务端认为没有"的幽灵物品。
覆盖虽然偶尔会让 UI 跳一下，但状态永远收敛到权威值。

**幂等键必需**：3 秒内玩家连点、或网络重试，必须靠 `idempotencyKey` 去重，否则一次点击扣两次钱。

## 6. Supabase 技术选型映射

| 需求 | Supabase 能力 |
|---|---|
| 权威计算（战斗/商店/升星） | **Edge Functions**（Deno，可直接跑 TS 版 `@arena/core`） |
| 存档（run / meta / 背包） | **Postgres** + RLS（行级安全，玩家只能读写自己的 run） |
| 账号 | **Auth**（匿名登录起步，后续可绑定第三方） |
| 排行榜 | Postgres 视图 + 物化视图定时刷新 |
| 防作弊 | Edge Function 内跑权威 sim + checksum 比对 |
| 实时（可选） | Realtime（观战 / 好友动态） |

**Deno 兼容性**：`@arena/core` 是纯 TS 无 Node API，可直接在 Deno 跑，无需转译。这是选 Supabase 的实际理由之一。

## 7. 前端瘦身后的职责边界

改造后前端**只做四件事**：

1. **渲染**：Canvas 画单位/地图/特效（`render/` 层完全不动）
2. **特效与音频**：消费后端结果 + 本地 sim 复现出的事件流
3. **输入采集**：把玩家操作转成 action 请求
4. **乐观 UI 与倒计时**：掩盖网络延迟的体验层

前端**不再做**：
- 判定胜负（后端权威）
- 计算金币/掉落/升星结果（后端权威）
- 生成 seed（后端分配）
- 决定商店库存（后端权威）

> 注意：前端**仍然保留完整的 BattleSim** —— 但它的角色从"裁判"变成"放映机"。
> 这正是本架构最优雅的地方：同一份代码，在后端是裁判，在前端是放映机。
