# 倒计时与请求时序设计

> 你的核心要求：**倒计时开始即发请求，倒计时结束即呈现结果**。
> 本质是**用玩家已经愿意等待的时间窗口，把网络延迟完全藏起来**。做对了，联机模式手感与单机无异。

---

## 0. 设计哲学：倒计时不是等待，是掩护

常见的错误做法是「点击 → 转圈等网络 → 出结果」。玩家能感知到网络存在，体验割裂。

本方案：

```
点击 → 立刻开始一段本地动画（5s 或 3s）
        ↑ 同一瞬间，请求已在飞
      → 动画结束时结果早已到达 → 直接呈现
```

关键数字：Supabase Edge Function 热实例 P50 约 80-150ms，P95 约 400ms。
**3 秒窗口能覆盖 P99.9 的网络延迟**，5 秒更是绰绰有余。
玩家永远看不到 loading，因为 loading 被伪装成了游戏的一部分。

## 1. 战斗 5 秒倒计时

### 1.1 状态机

```
        点击「开战」
             │
             ▼
    ┌─────────────────┐   请求已发出，倒计时并行
    │  COUNTING (5s)  │───────────────┐
    │  5…4…3…2…1      │               │
    └────────┬────────┘               ▼
             │              ┌──────────────────┐
             │              │ 后端权威结算      │
             │              │ genLayer         │
             │              │ makeAlly/Enemy   │
             │              │ BattleSim 跑完   │
             │              │ 写库 + 发奖       │
             │              └────────┬─────────┘
             │                       │ ~150ms 返回
             │              ┌────────▼─────────┐
             │              │ PRELOADED        │
             │              │ 本地跑 sim 校验   │
             │              │ checksum         │
             │              └────────┬─────────┘
             ▼                       │
    ┌─────────────────┐              │
    │ 倒计时归零       │◄─────────────┘
    └────────┬────────┘
             ▼
    ┌─────────────────┐
    │ 「开 战」横幅    │  0.6s
    └────────┬────────┘
             ▼
    ┌─────────────────┐
    │  PLAYING        │  播放本地复现的战斗
    └─────────────────┘
```

### 1.2 时间线（正常情况）

| 时刻 | 前端 | 后端 |
|---|---|---|
| `T+0ms` | 点击开战；倒计时动画启动（**5**）；发出 `battle.start` | — |
| `T+20ms` | 音效 `ui_click`，镜头拉近战场 | 收到请求，校验 run 状态 |
| `T+50ms` | — | `genLayer` + `makeAlly/makeEnemy` |
| `T+80ms` | — | **`BattleSim` 跑完整场（实测 3.3ms）** |
| `T+110ms` | — | 写 `battles` + 更新 `runs`（事务） |
| `T+150ms` | 收到 `BattleResultDTO`，静默预载 | 返回 |
| `T+160ms` | **本地跑同一份 sim**（3.3ms），比对 checksum | — |
| `T+1000ms` | 倒计时 **4** | — |
| `T+2000ms` | 倒计时 **3** | — |
| `T+3000ms` | 倒计时 **2** | — |
| `T+4000ms` | 倒计时 **1** | — |
| `T+5000ms` | 「开战」横幅 + `wave_start` 音效 | — |
| `T+5600ms` | 开始播放回放 | — |

**网络在 T+150ms 就完成了，玩家却要到 T+5000ms 才看到结果——4.85 秒的延迟预算全是富余。**

### 1.3 异常处理

| 情况 | 处理 |
|---|---|
| 倒计时归零但请求未返回 | 倒计时数字停在「0」，切「连接中…」+ 旋转指示器。**绝不用本地算的结果冒充** |
| 请求失败（网络） | 弹「重连」按钮，保留布阵，可重试（同一 `idempotencyKey`，不会重复结算） |
| 请求返回 `STATE_STALE` | 静默 `queryRun` 拉最新状态，回战前屏并提示「状态已更新」 |
| **本地 checksum ≠ 后端** | ⚠ 版本漂移。仍按**后端结果**呈现（权威），但上报埋点 + 提示「客户端需更新」 |
| 玩家中途退出 | 战斗已在 `battle.start` 时结算落库，重进直接看结果——**防止输了就拔网线** |

> 最后一条是关键的防作弊设计：**结算发生在开战瞬间，不是播放结束时**。
> 玩家看到的播放只是"回放一个已经发生的事实"。

### 1.4 前端实现骨架

```ts
type Phase = 'idle' | 'counting' | 'waiting' | 'banner' | 'playing' | 'error';

function useBattleCountdown(backend: GameBackend, runId: string) {
  const [phase, setPhase]   = useState<Phase>('idle');
  const [count, setCount]   = useState(5);
  const resultRef = useRef<BattleResultDTO | null>(null);

  const start = useCallback(async (formation: Record<string, Vec2>) => {
    setPhase('counting');
    setCount(5);
    resultRef.current = null;

    // ① 请求与倒计时同时启动 —— 这一行是整个设计的核心
    const pending = backend.startBattle({
      runId,
      formation,
      idempotencyKey: crypto.randomUUID(),
      coreVersion: CORE_VERSION,
      clientTs: Date.now(),
    });

    // ② 本地倒计时（不 await 网络）
    const tick = setInterval(() => setCount((c) => c - 1), 1000);

    // ③ 网络回来就静默预载 + 本地校验
    pending.then((res) => {
      if (!res.ok) { setPhase('error'); return; }
      resultRef.current = res.data;
      // 本地复现，比对 checksum（用 Web Worker，不阻塞倒计时动画）
      verifyInWorker(res.data.replay).then((localChecksum) => {
        if (localChecksum !== res.data.replay.checksum) {
          reportDrift(res.data.battleId, localChecksum);   // 埋点，不打断玩家
        }
      });
    });

    // ④ 5 秒后：有结果就开打，没结果就等
    await sleep(5000);
    clearInterval(tick);
    if (!resultRef.current) {
      setPhase('waiting');
      const res = await pending;              // 已在飞的同一个 Promise
      if (!res.ok) { setPhase('error'); return; }
      resultRef.current = res.data;
    }
    setPhase('banner');
    await sleep(600);
    setPhase('playing');
  }, [backend, runId]);

  return { phase, count, result: resultRef, start };
}
```

**注意 ③ 用 Web Worker 跑校验**：本地复现虽只要 3.3ms，但在低端手机上可能到 30-50ms，
在主线程跑会让倒计时动画掉帧。倒计时动画的流畅度是这个设计的门面，不能省。

## 2. 商店类操作 3 秒倒计时

### 2.1 与战斗的本质差异

战斗是**一次性、不可撤销、玩家已预期要等**的重操作。
商店购买是**高频、连续、玩家期望即时反馈**的轻操作。

所以商店**不能**用"等 3 秒才更新 UI"——那样玩家买 10 件装备要等 30 秒，体验灾难。

**正确做法：乐观 UI + 3 秒确认窗**

```
点击购买
  ├─→ t=0ms   UI 立即更新（金币-price，物品入包），按钮进入 "确认中 3…2…1"
  ├─→ t=0ms   请求发出
  ├─→ t~150ms 后端权威状态返回，暂存（不立即覆盖，避免 UI 跳变）
  └─→ t=3000ms 倒计时结束 → 用权威状态平滑覆盖 → 显示 ✓
```

玩家的**操作节奏完全不受阻塞**——可以连续点，每个操作各自独立跑自己的 3 秒确认。

### 2.2 为什么倒计时结束才覆盖而非立即覆盖

若 150ms 就用权威状态覆盖，会出现**数字闪跳**：
乐观算的金币 1240 → 权威值 1238（比如折扣算法有 1 金币的舍入差）→ 玩家看到数字抖一下。

延到 3 秒后覆盖，配合一个「结算完成」的微动效，抖动被动效掩盖，观感是"结算确认"而非"算错了"。

### 2.3 状态机

```
IDLE ──点击──► OPTIMISTIC (UI已更新, 倒计时3s, 请求在飞)
                    │
        ┌───────────┼────────────┐
        │           │            │
    权威返回OK   权威拒绝      超时/网络错
        │           │            │
        ▼           ▼            ▼
   倒计时归零     立即回滚      立即回滚
   平滑覆盖       +错误提示     +重试按钮
        │           │            │
        ▼           ▼            ▼
      CONFIRMED   ROLLED_BACK  RETRYABLE
```

**拒绝时立即回滚，不等倒计时**：错误必须尽快让玩家知道，
让他对着一个"其实没买成"的界面数 3 秒是纯粹的伤害。

### 2.4 幂等与连点

3 秒窗口内玩家可能：
- 连点同一个「购买」按钮 5 次
- 网络重试

`idempotencyKey` **在按钮首次点击时生成一次**，后续重试复用同一个 key：

```ts
function useIdempotentAction<T>(fn: (key: string) => Promise<Result<T>>) {
  const keyRef = useRef<string | null>(null);
  const run = async () => {
    keyRef.current ??= crypto.randomUUID();   // 只在首次生成
    const res = await fn(keyRef.current);
    if (res.ok) keyRef.current = null;        // 成功后释放，下次是新操作
    return res;
  };
  return run;
}
```

服务端命中 `idempotency_keys` 表时，直接返回缓存的首次响应，**不重复扣钱**。

### 2.5 各操作的倒计时时长建议

不是所有操作都该是 3 秒。按**操作的重量**分级：

| 操作 | 倒计时 | 理由 |
|---|---|---|
| 购买 / 出售装备 | **3s** | 你指定的标准值 |
| 刷新商店 / 刷新招募 | **3s** | 同上，且刷新有"抽卡"感，倒计时增强期待 |
| **升星 / 属性突破** | **3s** | 结果有随机性（突破属性随机），倒计时 = 开奖仪式 |
| 锻造 / 属性转移 / 合成 | **3s** | 有成功率，是最需要仪式感的操作 |
| 穿戴 / 卸下装备 | **0s（即时）** | 纯状态整理，无随机性、无消耗。加倒计时纯属折磨 |
| 开箱 | **1.2s** | 有开箱动画，动画本身就是倒计时 |
| 使用消耗品 | **3s** | 成长药剂有随机属性 |

**原则：有随机性或有消耗的操作才配倒计时；纯整理性操作必须即时。**
一键装备 42 件若每件 3 秒，那是 126 秒——荒谬。所以 `equipAll` 也应是即时的。

## 3. 统一的操作封装

把上面两套时序抽象成一个 hook，全站复用：

```ts
interface TimedActionOpts<T> {
  /** 倒计时秒数；0 = 即时 */
  countdown: number;
  /** 乐观更新：立即改本地 UI，返回回滚函数 */
  optimistic?: () => () => void;
  /** 实际请求 */
  request: (key: string) => Promise<Result<T>>;
  /** 权威状态到达且倒计时结束后的应用 */
  commit: (data: T) => void;
}

function useTimedAction<T>(opts: TimedActionOpts<T>) {
  const [state, setState] = useState<'idle'|'pending'|'ok'|'error'>('idle');
  const [left, setLeft] = useState(0);
  const keyRef = useRef<string|null>(null);

  const fire = async () => {
    if (state === 'pending') return;
    setState('pending');
    keyRef.current ??= crypto.randomUUID();

    const rollback = opts.optimistic?.();          // ① 乐观更新
    const pending  = opts.request(keyRef.current); // ② 请求起飞

    let timer: ReturnType<typeof setInterval> | undefined;
    if (opts.countdown > 0) {                      // ③ 倒计时
      setLeft(opts.countdown);
      timer = setInterval(() => setLeft((v) => Math.max(0, v - 1)), 1000);
    }

    const res = await pending;
    if (!res.ok) {                                 // ④ 失败：立即回滚
      clearInterval(timer);
      rollback?.();
      setState('error');
      return res;
    }
    // ⑤ 成功：等倒计时走完再覆盖
    const remain = opts.countdown * 1000 - elapsed();
    if (remain > 0) await sleep(remain);
    clearInterval(timer);
    opts.commit(res.data);
    keyRef.current = null;
    setState('ok');
    return res;
  };

  return { fire, state, left };
}
```

使用：

```tsx
const buy = useTimedAction({
  countdown: 3,
  optimistic: () => {                       // 乐观扣钱
    const prev = gold;
    setGold(gold - price);
    return () => setGold(prev);             // 回滚函数
  },
  request: (key) => backend.buyItem({ runId, itemId, idempotencyKey: key, coreVersion }),
  commit: (snap) => applySnapshot(snap),    // 权威覆盖
});

<button onClick={buy.fire} disabled={buy.state === 'pending'}>
  {buy.state === 'pending' ? `确认中 ${buy.left}…` : `购买 ${price}💰`}
</button>
```

## 4. 本地模式下的倒计时

**本地模式必须保留完全相同的倒计时**，尽管 `LocalBackend` 是同步的（<1ms 返回）。

理由：
1. **游戏节奏是设计的一部分**，不是网络的副产品。5 秒备战倒计时给玩家看阵容、建立预期。
2. **两条通路体验必须一致**，否则本地测出来的手感在线上不成立。

实现上 `LocalBackend` 不需要假装延迟——倒计时由**前端 hook** 控制，与后端快慢无关。
`useTimedAction` 里 `await sleep(remain)` 那一行天然处理了这件事：
本地模式 `remain ≈ 3000ms`（因为请求 0ms 就回来了），照样等满 3 秒。

> 反过来说：**绝不要在 LocalBackend 里 `sleep` 假装网络延迟**。
> 那会污染单测（10,080 场封测每场等 5 秒 = 14 小时）。
> 延迟属于表现层，必须留在前端 hook 里，且测试时可通过 `countdown: 0` 关闭。

## 5. 埋点与可观测性

倒计时方案的健康度靠这几个指标监控：

| 指标 | 含义 | 告警阈值 |
|---|---|---|
| `battle_resp_ms` P95 | 开战请求耗时 | > 3000ms（吃掉倒计时余量） |
| `battle_timeout_rate` | 倒计时归零仍未返回的比例 | > 0.5% |
| `checksum_mismatch_rate` | 前后端复现不一致比例 | **> 0（任何一例都要查）** |
| `idem_hit_rate` | 幂等键命中率（连点/重试） | 正常 3-8%，突增说明有重试风暴 |
| `optimistic_rollback_rate` | 乐观更新回滚率 | > 2%（说明客户端预测逻辑与服务端规则不一致） |

最后一条特别有价值：**回滚率高说明前端的乐观计算与后端规则漂移了**，
是规则重复实现的早期信号——提醒你某处又写了第二份规则。
