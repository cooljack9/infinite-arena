# Supabase 数据库设计

> Postgres schema + RLS + 索引。原则：**run 的高频可变部分用 JSONB，需要查询/排行的字段用列**。

---

## 0. 设计取舍说明

现状是 `run` 全部存内存、`meta` 存 5 个 localStorage key。服务器化后需要落库。

**为什么 run 用 JSONB 而不是全部拆表**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 全拆表（heroes / inventory / equipped 各一表） | 可查询、可索引 | 一次商店购买要写 3-5 张表，需事务；且这些数据**只有本人读**，查询需求为零 |
| **全 JSONB 单行** | 一次 UPDATE 搞定，天然原子 | 无法按装备属性查询 |
| **混合（采纳）** | 排行/统计字段拆列，其余 JSONB | 略有冗余 |

选混合：`layer` / `score` / `mode` / `status` 拆列（排行榜要查），其余塞 JSONB。
一局游戏的状态是**强内聚的整体**，拆开只会制造分布式事务问题而换不来任何查询能力。

## 1. 表结构

### 1.1 `profiles` — 玩家账号

```sql
create table public.profiles (
  id           uuid primary key references auth.users(id) on delete cascade,
  display_name text        not null default '无名勇者',
  created_at   timestamptz not null default now(),
  updated_at   timestamptz not null default now()
);
```

### 1.2 `player_meta` — 账号级元进度（对应现 localStorage）

```sql
create table public.player_meta (
  user_id          uuid primary key references public.profiles(id) on delete cascade,
  best_layer       int  not null default 0,
  endless_unlocked bool not null default false,
  team_presets     jsonb not null default '[]'::jsonb,   -- TeamPreset[]
  prefs            jsonb not null default '{"battleSpeed":1,"colorblind":false}'::jsonb,
  total_runs       int  not null default 0,
  total_wins       int  not null default 0,
  updated_at       timestamptz not null default now()
);

create index on public.player_meta (best_layer desc);   -- 排行榜
```

### 1.3 `runs` — 一局游戏（核心表）

```sql
create type run_status as enum ('active','won','lost','abandoned');
create type game_mode  as enum ('novice','normal','ironman');

create table public.runs (
  id          uuid primary key default gen_random_uuid(),
  user_id     uuid not null references public.profiles(id) on delete cascade,

  -- 拆列：排行榜/统计要查
  mode        game_mode  not null,
  status      run_status not null default 'active',
  layer       int        not null default 1,
  score       int        not null default 0,
  failures    int        not null default 0,

  -- 权威种子：绝不下发给客户端明文（客户端只拿派生后的 battleSeed）
  seed        bigint     not null,

  -- 乐观锁：每次写 +1，客户端提交时带上，不匹配则 STATE_STALE
  version     int        not null default 0,

  -- JSONB：强内聚的局内状态
  team        jsonb not null default '[]'::jsonb,   -- HeroDef[]（含 uid/star/growthBonus/mount）
  economy     jsonb not null default '{}'::jsonb,   -- gold/inventory/equipped/shopStock/...
  relics      jsonb not null default '[]'::jsonb,
  progress    jsonb not null default '{}'::jsonb,   -- resolvedEvents/forgedThisLayer/fusedThisLayer

  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now()
);

-- 一个玩家同时只允许一局 active（防止多开刷资源）
create unique index runs_one_active
  on public.runs (user_id) where status = 'active';

create index on public.runs (user_id, created_at desc);
create index on public.runs (mode, layer desc) where status in ('won','lost');
```

> **`seed` 不下发**是关键的防作弊设计。客户端若拿到 run seed，就能本地枚举出未来所有层的
> Boss 编成、掉落、商店库存。客户端只应拿到**当前这一场**的 `battleSeed`（已派生），
> 用完即弃，无法反推根种子。

### 1.4 `battles` — 战斗记录（权威结算 + 回放）

```sql
create table public.battles (
  id            uuid primary key default gen_random_uuid(),
  run_id        uuid not null references public.runs(id) on delete cascade,
  user_id       uuid not null references public.profiles(id) on delete cascade,

  layer         int  not null,
  battle_seed   bigint not null,
  result        text not null check (result in ('win','lose')),
  total_ticks   int  not null,
  duration_sec  numeric(6,2) not null,

  -- 权威校验和：客户端 ack 时比对，不一致说明版本漂移
  checksum      text not null,
  client_checksum text,
  checksum_match  bool,

  -- 回放输入（足以完整复现，约 2-6KB）
  replay_input  jsonb not null,   -- { allies, enemies, arena, buildings, buildingScale }
  -- 结算产出
  outcome       jsonb not null,   -- { stats, mvp, killGains, deadAllyUids }

  created_at    timestamptz not null default now()
);

create index on public.battles (run_id, layer);
create index on public.battles (user_id, created_at desc);
-- 版本漂移监控：灰度期盯这个
create index on public.battles (checksum_match) where checksum_match = false;
```

**为什么存 `replay_input` 而不存事件流**：见架构总览 §0，事件流 111KB vs 回放输入 2-6KB。
存回放输入还有额外好处：**将来引擎升级后可以重跑历史战斗做回归对比**。

### 1.5 `idempotency_keys` — 幂等去重

```sql
create table public.idempotency_keys (
  key         text primary key,
  user_id     uuid not null references public.profiles(id) on delete cascade,
  action      text not null,
  -- 缓存首次执行的完整响应，重复请求直接回放
  response    jsonb not null,
  created_at  timestamptz not null default now()
);

create index on public.idempotency_keys (created_at);
-- 定时清理 24h 前的键（pg_cron）
```

这张表是 3 秒倒计时方案的**安全底座**：玩家在倒计时内连点 5 次购买，
5 个请求带同一个 `idempotencyKey`，只有第一个真正执行，其余直接返回缓存响应。

### 1.6 `leaderboard` — 排行榜（物化视图）

```sql
create materialized view public.leaderboard as
select
  r.user_id,
  p.display_name,
  r.mode,
  max(r.layer)  as best_layer,
  max(r.score)  as best_score,
  count(*)      as runs
from public.runs r
join public.profiles p on p.id = r.user_id
where r.status in ('won','lost')
group by r.user_id, p.display_name, r.mode;

create unique index on public.leaderboard (user_id, mode);
create index on public.leaderboard (mode, best_layer desc, best_score desc);

-- pg_cron 每 5 分钟刷新
select cron.schedule('refresh-leaderboard','*/5 * * * *',
  $$refresh materialized view concurrently public.leaderboard$$);
```

## 2. RLS 策略

**全部表默认拒绝，逐条放行。** 写操作一律不给客户端直连——只能走 Edge Function（service_role）。

```sql
alter table public.profiles          enable row level security;
alter table public.player_meta       enable row level security;
alter table public.runs              enable row level security;
alter table public.battles           enable row level security;
alter table public.idempotency_keys  enable row level security;

-- profiles：只读写自己
create policy "own profile read"  on public.profiles
  for select using (auth.uid() = id);
create policy "own profile write" on public.profiles
  for update using (auth.uid() = id);

-- player_meta：只读自己（写由 Edge Function 用 service_role 执行）
create policy "own meta read" on public.player_meta
  for select using (auth.uid() = user_id);

-- runs：只读自己的局
create policy "own runs read" on public.runs
  for select using (auth.uid() = user_id);

-- battles：只读自己的战斗
create policy "own battles read" on public.battles
  for select using (auth.uid() = user_id);

-- idempotency_keys：客户端完全不可见
-- （不建任何 policy = 全部拒绝，仅 service_role 可访问）
```

**关键纪律：客户端对 `runs` / `player_meta` 只有 SELECT，没有 UPDATE。**
所有写入必须经 Edge Function 的规则校验。
若给客户端 UPDATE 权限，玩家直接改 `gold` 字段就完事了——RLS 只能限制"改谁的行"，
不能限制"改成什么值"。

## 3. 关键存储过程

### 3.1 乐观锁更新（防并发覆盖）

```sql
create or replace function public.update_run_versioned(
  p_run_id     uuid,
  p_expect_ver int,
  p_patch      jsonb
) returns public.runs
language plpgsql security definer as $$
declare
  v_row public.runs;
begin
  update public.runs
     set team     = coalesce(p_patch->'team',     team),
         economy  = coalesce(p_patch->'economy',  economy),
         relics   = coalesce(p_patch->'relics',   relics),
         progress = coalesce(p_patch->'progress', progress),
         layer    = coalesce((p_patch->>'layer')::int,    layer),
         score    = coalesce((p_patch->>'score')::int,    score),
         failures = coalesce((p_patch->>'failures')::int, failures),
         status   = coalesce((p_patch->>'status')::run_status, status),
         version  = version + 1,
         updated_at = now()
   where id = p_run_id
     and version = p_expect_ver      -- ← 乐观锁
  returning * into v_row;

  if not found then
    raise exception 'STATE_STALE' using errcode = 'P0001';
  end if;
  return v_row;
end $$;
```

### 3.2 战斗结算原子写入

战斗结算要同时写 `battles` + 更新 `runs` + 可能更新 `player_meta.best_layer`，
必须在一个事务里，否则会出现"战斗记录有了但奖励没发"。

```sql
create or replace function public.commit_battle(
  p_run_id      uuid,
  p_expect_ver  int,
  p_battle      jsonb,     -- battles 表字段
  p_run_patch   jsonb      -- runs 的新状态
) returns jsonb
language plpgsql security definer as $$
declare
  v_run    public.runs;
  v_bid    uuid;
  v_uid    uuid;
begin
  select user_id into v_uid from public.runs where id = p_run_id;

  insert into public.battles (
    run_id, user_id, layer, battle_seed, result,
    total_ticks, duration_sec, checksum, replay_input, outcome
  ) values (
    p_run_id, v_uid,
    (p_battle->>'layer')::int,
    (p_battle->>'battle_seed')::bigint,
    p_battle->>'result',
    (p_battle->>'total_ticks')::int,
    (p_battle->>'duration_sec')::numeric,
    p_battle->>'checksum',
    p_battle->'replay_input',
    p_battle->'outcome'
  ) returning id into v_bid;

  v_run := public.update_run_versioned(p_run_id, p_expect_ver, p_run_patch);

  -- 最佳层推进（只增不减）
  update public.player_meta
     set best_layer = greatest(best_layer, v_run.layer),
         endless_unlocked = endless_unlocked
           or (v_run.mode = 'novice' and v_run.status = 'won'),
         updated_at = now()
   where user_id = v_uid;

  return jsonb_build_object('battleId', v_bid, 'run', to_jsonb(v_run));
end $$;
```

## 4. JSONB 内部结构

```jsonc
// runs.economy
{
  "gold": 1240,
  "inventory": [ /* Equipment[] */ ],
  "pendingDrops": [ /* Chest[] */ ],
  "equipped": { "H12": [ /* ≤6 件 */ ] },
  "consumables": [ /* ConsumableItem[] */ ],
  "shopStock": { "equipment": [], "consumables": [] },
  "recruitPool": [ /* HeroDef[] */ ],
  "tradeCount": 17,
  "refreshCount": 42,
  "opSeq": 128            // 新增：替代 inventory.length 入种子（见接口契约 §4.1）
}

// runs.progress
{
  "resolvedEvents": [7, 13, 16],
  "forgedThisLayer": ["eq_abc"],
  "fusedThisLayer": 1,
  "heroUidSeq": 14        // 新增：队伍成员 uid 分配器（原模块级变量，改为随 run 持久化）
}
```

> `heroUidSeq` 落库是 P0-1 改造的一部分：原来是模块级 `let heroUidSeq = 0`，
> 刷新页面就重置，同一局里可能分配出重复 uid。落库后按 run 隔离且持久。

## 5. 容量估算

单个 run 的 JSONB 体积：

| 字段 | 满编估算 |
|---|---|
| `team`（7 英雄，含 growthBonus/mount） | ~6 KB |
| `economy.equipped`（7×6=42 件装备） | ~14 KB |
| `economy.inventory`（背包 50 件） | ~17 KB |
| 其余 | ~3 KB |
| **合计** | **~40 KB/run** |

battles 每层一条 ~5 KB，500 层深塔 = 2.5 MB。

Supabase 免费额度 500MB → 约可存 **1 万个完整 run**（含战斗记录）。
建议：`battles` 只保留最近 50 层 + 所有 Boss 层，其余定期归档或删除。

```sql
-- pg_cron 每天清理：非 Boss 层且超过 50 层之前的战斗记录
select cron.schedule('prune-battles','0 4 * * *', $$
  delete from public.battles b
  using public.runs r
  where b.run_id = r.id
    and b.layer % 5 <> 0
    and b.layer < r.layer - 50
$$);
```
