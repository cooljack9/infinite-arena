# 改造实施路线

> 原则：**任何一个阶段结束时，游戏都必须是可玩的**。不接受"重构中，暂时跑不起来"。
> 每阶段都有可执行的验收标准，`npm run verify` 必须始终全绿。

---

## 阶段 0：修确定性漏洞（P0，1-2 天）

**这是唯一的阻塞项。** 不修完，后面所有权威校验都是空中楼阁。

### 0.1 模块级计数器改实例级

| 文件 | 现状 | 改法 |
|---|---|---|
| `src/game/engine/unit.ts:16` | `let uid = 0` | 引入 `IdGen` 接口，`makeAlly/makeEnemy` 接受 `idGen` 参数 |
| `src/game/engine/battle/common.ts:20` | `let bId = 0` | 计数器挂 `BattleSim` 实例（照抄已做对的 `spawnSeq`） |
| `src/game/state/slices/helpers.ts:113` | `let heroUidSeq = 0` | 落到 `run.progress.heroUidSeq`，随存档持久化 |

```ts
// src/game/engine/ids.ts（新增）
export interface IdGen { next(prefix: string): string }
export class SeqIdGen implements IdGen {
  constructor(private n = 0) {}
  next(p: string) { return `${p}${this.n++}`; }
  /** 存档恢复用 */
  get cursor() { return this.n; }
}
```

**兼容性**：`makeAlly(h, lvl, eqs, opt, idGen?)` 的 `idGen` 设为可选，缺省时退化到旧全局计数器。
这样现有 6 个调用点可以逐个迁移，不需要一次性大改。迁移完成后再把参数改为必填。

### 0.2 清除 `Math.random`

```ts
// src/game/state/slices/run.ts:180 —— 真实漏洞（非兜底路径）
// ❌ const k = PRIMARY_KEYS[Math.floor(Math.random() * PRIMARY_KEYS.length)];
// ✅
const mvpRng = mulberry32((run.seed ^ (currentLayer * 0x1b873593) ^ hashStr(mvpUid)) >>> 0);
const k = PRIMARY_KEYS[Math.floor(mvpRng() * PRIMARY_KEYS.length)];
```

`run.ts:30` 的 run seed 生成：本地模式保留 `Math.random`（这是**根熵源**，合理），
远程模式改由后端分配。

`economy.ts` 的 4 处兜底：改为 `if (!run) return;` 直接拒绝——
没有 run 却在买东西本身就是 bug，静默随机只会掩盖它。

### 0.3 验收

把本次写的确定性探针固化进 CI：

```bash
npm run verify        # 现有四道闸门必须仍全绿
npm run probe         # 新增：12 项确定性断言（本次已验证可通过）
```

探针内容（已实测）：
- [A] 5 组 seed×layer，逐 tick bit 级复现 —— **id 不再需要归一化即应通过**
- [B] 交错执行互不污染
- [C] 回放包体积 < 5KB
- [D] 校验和对 seed/layer/阵容变化敏感

> 阶段 0 完成的硬标志：**探针不做 id 归一化也能 12/12 通过**。
> 本次实测是归一化后才通过的，说明 id 问题真实存在。


### 1.2 规则函数的签名纪律

**所有规则函数必须是纯函数：`(state, input) => Result<state>`**

```ts
// packages/core/src/rules/economy.ts
export function buyItem(s: RunState, itemId: string): Result<RunState> {
  const item = findInShop(s, itemId);
  if (!item) return err('ITEM_GONE');
  const price = Math.round(item.basePrice * (1 - discountOf(s.tradeCount)));
  if (s.gold < price) return err('INSUFFICIENT_GOLD');
  return ok({
    ...s,
    gold: s.gold - price,
    inventory: [...s.inventory, item],
    tradeCount: s.tradeCount + 1,
    shopStock: removeFromStock(s.shopStock, itemId),
  });
}
```

不碰 IO、不碰 zustand、不碰 `Date.now()`。
这样同一个函数在浏览器、Deno、Node 单测里跑出完全一样的结果。

### 1.3 store 变成薄壳

现有 zustand store 的 action 从"实现规则"退化为"调用后端 + 应用快照"：

```ts
// ❌ 现状：store 里实现规则
buyItem: (id) => { /* 30 行规则逻辑 */ }

// ✅ 改造后
buyItem: async (id) => {
  const res = await backend.buyItem({ runId, itemId: id, idempotencyKey, coreVersion });
  if (res.ok) set(applySnapshot(res.data));
  else set({ lastError: res });
}
```

**store 里不再有任何数值计算。** 这是判断阶段 1 是否完成的标准：
在 `src/game/state/` 下 grep 不到任何 `Math.round` / 价格公式 / 概率判定。

### 1.4 验收

- `npm run verify` 全绿（`@arena/core` 内跑）
- 游戏在 `LocalBackend` 下**功能完全不变**，玩家无感
- `packages/core/package.json` 的 `dependencies` 为空
- core 可在 Deno 下直接 import 无报错：`deno check packages/core/src/index.ts`

### 灰度策略

```ts
const backend = pickBackend({
  // 环境变量控制，可随时切回本地
  mode: import.meta.env.VITE_BACKEND ?? 'local',
});
```

**双跑比对期（重要）**：上线前一周，`RemoteBackend` 内部**同时**跑本地 core 计算，
比对两侧结果，不一致就上报但**以远端为准**：

```ts
async buyItem(req) {
  const remote = await this.http('shop.buy', req);
  if (import.meta.env.DEV) {
    const local = rules.buyItem(this.cachedState, req.itemId);
    if (!deepEqual(local, remote.data)) reportDivergence('shop.buy', local, remote);
  }
  return remote;
}
```

这能在真实流量下抓出"服务端与客户端规则漂移"，比任何单测都有效。

### 验收

- `optimistic_rollback_rate` < 2%
- 断网重连后状态正确恢复
- 同一账号双开时，第二个 `startRun` 被 `runs_one_active` 唯一索引拒绝

## 阶段 4：数值平衡修复（可与 1-3 并行）

封测报告的 P0/P1 与架构无关，但服务器化后**改数值不需要发版**——
把 `tuning.json` 从静态文件改为数据库配置表，即可热更新。

| 级别 | 问题 | 建议 |
|---|---|---|
| P0 | titan Boss 层胜率 8.1%（普通层 38.9%） | titan 周期 5→10，`bossComp` 0.75/0.9/1.0 |
| P0 | 玩家成长仅敌人 38%，平均只推进 4.86 层 | `lvl = layer`（现为 `1+⌊(L-1)/2⌋`），目标比值 0.75-0.85 |
| P0 | L10/20/30 三重规则叠加，L30 全败 | `isMutation` 改 `n%10===5` 错开半周期 |
| P1 | summoner 统治（+11.0pp） | 继承系数 −20~25% |
| P1 | charge 负收益（−6.9pp） | 落地 1.5s 减伤 40% |
| P1 | 6 特性零触发（坚壁/大招/闪避/龙吐息/击倒/击退） | **优先排查"大招"，疑似功能 bug** |

> 最后一条建议在阶段 0 就顺手查一下：如果大招真的从未释放，
> 那么现在所有的数值结论都建立在一个残缺的战斗模型上。

## 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| **`inventory.length` 入种子** | 背包不同步 → 锻造结果分歧 | 改用 `opSeq` 单调计数（接口契约 §4.1） |
| 前后端 core 版本漂移 | 回放对不上 | `coreVersion` 强校验 + checksum 监控 + 强制更新提示 |
| Edge Function 冷启动 | 首次操作 300ms+ | 单函数多 action 共享热实例；倒计时窗口足以吸收 |
| JSONB 行过大（满编 ~40KB） | 更新慢 | 已估算可接受；若超 100KB 再考虑拆 `inventory` 单表 |
| 玩家断线导致 run 卡 active | 无法开新局 | `runs_one_active` + 提供"放弃当前局"入口 |
| 存档迁移（现有 localStorage 玩家） | 老玩家进度丢失 | 首次登录时把 localStorage 的 `ia_best`/`ia_presets` 上传合并 |
