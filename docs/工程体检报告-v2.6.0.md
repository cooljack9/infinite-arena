## 一句话结论

**内容骨架设计克制且有据可循，但"落地层"与"内容层"严重脱节**——28 个技能定义里 7 个在引擎中无分支（纯文案），18 种常规怪只有 2 种按设计工作；而 UI 层刚加入的全局 zoom 缩放方案引入了 3 个阻断级回归。

最要命的四件事：**无尽模式 94% 的层是同一张关卡**（30~500 层被 `DEMO_CAP` 压成一层）、**敌方技能打自己人**（阵营硬编码）、**归来者第一次挨打就"复活"**、**爆伤在开战瞬间凭空蒸发 38%**。

## 二、P0 阻断问题

### 🔴 UI-1 ｜ 全局 zoom 把移动端正文缩到 ~6px（**本轮 Q4 新增，回归**）

- `src/index.css:188-192` `#root { width:760px; max-width:none }`（旧为 `width:100%; max-width:760px`）
- `src/render/fitScreen.ts:14-16` `s = vw / 760`，夹 0.42~2.2
- `src/index.css:64` 字号 `--fs-xs:11px; --fs-sm:12px; --fs-md:13px`

390px 手机 → zoom=0.513 → 12px 正文实际 **6.2px**；而 `@media (max-width:560px)`（`index.css:856`）还会**二次**压字号，形成叠加缩小。等于用等比缩放换掉了整套响应式设计。

**建议**：zoom 只承担"放大"方向（下限设 1），窄屏回到流式布局 + 媒体查询，两套逻辑不要叠在同一套断点上。

### 🔴 UI-2 ｜ 战斗全屏层 `100vw/100dvh` 与 zoom 二次叠乘 → 桌面端战斗 UI 出屏

- `src/index.css:1000-1011` `.battle-stage { width:100vw; height:100dvh }`
- `src/index.css:1032-1064` HUD / 倍速条 / 技能条全为 `left:50%; translateX(-50%)`

`vw/dvh` **先按视口解析、再乘 zoom**：视口 1000px → zoom=1.316 → 舞台实际渲染 **1316px**，超出视口 316px；HUD 的 `left:50%` 锚点随之右移、偏离甚至移出屏幕，超出部分被 `overflow-x:hidden` 裁掉且无法滚动。只有视口恰好 760px 才正确。**战斗是核心屏。**

**建议**：战斗层改回 `inset:0` + auto 尺寸，或把 zoom 系数写进 CSS 变量自行换算。

### 🔴 UI-3 ｜ 不支持 zoom 的浏览器无任何回退 → Android Firefox 整屏被裁、不可玩

- `fitScreen.ts` 注释称"回退为 760px 固定宽（等同旧行为）"，但**实现里没有任何 `@supports` 检测**（全仓 `@supports` 0 处），且"760px 固定宽"**不等于**旧的 `width:100%`
- 390px 视口下 760px 的 `#root` 有 370px 落屏外，被 `overflow-x:hidden` 永久裁掉 → 右侧"开战/下一层"按钮点不到

**建议**：`CSS.supports('zoom','1.5')` 判定，不支持时还原 `#root{width:100%;max-width:760px}`。

### 🔴 内容-1 ｜ `DEMO_CAP=30` 冻结整个关卡生成：30~500 层是同一张关卡

- `packages/core/src/gen/levelGen.ts:262-263` `const clamped = Math.min(n, DEMO_CAP)`（`DEMO_CAP=30`）
- `scaling.ts:69` 定义；`ENDLESS_CAP=500`

实测（seed=12345）：layer 30 / 50 / 500 的 `boss=strong, elite=true, vac=true, mut=true, waves=[8/8/1], budget=392` **完全相同**。

影响：一局 500 层里 **471 层（94%）是同一个关卡**；事件在深层出现 **0 次**（4 个事件内容深层完全作废）；而 `rules/index.ts:283` 用的是**未 clamp** 的 `enemyScale`，数值仍在涨到 13× → **"数值在涨、内容不变"**，后期必然无聊化。

**建议**：把 `DEMO_CAP` 从内容生成里摘出去（仅保留给集成测试作循环上界），让 `bossTierAt / buildWaves / rollRandomEvent / isVacuum` 吃真实层号。

### 🔴 内容-2 ｜ `castSkill` 阵营硬编码：敌方技能打自己人（含自伤）

- `packages/core/src/engine/battle.ts:1587-1588`
  ```ts
  const enemies = this.alive('enemy');   // 绝对阵营，不是 u 的对立面
  const allies  = this.alive('ally');
  ```
  对比同文件 `:440/:474/:1956/:2094` 正确写法 `this.alive(u.side === 'ally' ? 'enemy' : 'ally')`

于是 `taunt`（嘲讽+震荡波伤自己人）、`charge`（突进己方 250% 物伤）、`barrage`（5 连射随机打己方）、`deadshot`（专打己方残血）、`timelock`、`hexburst` 全部反向。

实测（seed=777）：出现 `钢盾狂战 dmg 钢盾狂战`（自伤）、`狂暴战士 dmg 突袭兵` 等敌→敌伤害事件。

影响：18 种常规怪里**只有 2 种按设计工作**（`咒法石像` ward、`亡灵术士` summon），其余 **9 种反向误伤、6 种空放**。整条难度曲线（含 `enemyScale`/`segmentMult` 精心调参）建立在错误行为之上。

**建议**：改相对阵营 `foes = this.alive(u.side === 'ally' ? 'enemy' : 'ally')`、`friends = this.alive(u.side)`，`inCastRange` 排除自身；加单测断言"attacker.side === target.side 的伤害事件数 = 0"。

### 🔴 内容-3 ｜ 归来者第一次挨打就触发"复活"，而非死亡时

- `packages/core/src/engine/battle.ts:722-748`，`applyDamage` 末尾 `:1257` **无条件调用**（无 hp<=0 门控）

```ts
if (u.side === 'ally' && u.traitId === 'returner' && ...) {   // 归来者分支
  u.hp = u.maxHp * 0.6; ...
}
if (u.hp > 0 || !u.alive) return;   // ← 血线检查在特性分支之后
```

实测：英雄 hp=576/630 挨一下 → 触发"复活"，血被**强制设为 378**（比挨打前还低 40%），`returnerUsed=1` 永久消耗。

影响：复活机制等于不存在；满血挨小伤反而掉血 40%；白送成长 +4%/体型 +30%/射程 +2%；`returnerDrain` 每秒流失 8% 最大生命约 7.5 秒后必真死（且复活已用完）；铁人模式 `deadAllies.delete` 抹掉 permadeath 记账。

**建议**：在特性分支前加 `if (u.hp > 0 || !u.alive) return;`，并把调用改为 `if (target.hp <= 0) this.killIfDown(...)`。

### 🔴 内容-4 ｜ 7 个已定义技能在 `castSkill` 无分支，也无 `default`

`battle.ts:1618-2272` switch 缺 case：`m_witch_skill`（咒怨召唤）、`m_demon_skill`（炼狱爆发）、`m_skel_skill`（骸骨突袭）、`m_garg_skill`（石化咆哮）、`m_wolf_demon_skill`、`m_wolf_fae_skill`、**`m_angel_skill`（Boss 堕天炽天使）**。

这些技能仍走完 `shouldCast`（`default: return true`）→ 扣 CD、画起手环、发音效，**然后什么都不做**。

实测：属性更强的 `堕天炽天使`（colossal `base(18,6,5,18)`）98 tick 只造成 70 伤害，属性更弱的 `预言魔像` 造成 216。

**建议**：补 case（多可复用现有骨架：`m_skel_skill`→charge、`m_garg_skill`→taunt），并加静态校验"每个 SkillDef.id 必须在 castSkill 有分支"。

## 四、P2 优化项（节选）

**UI 侧**：24 个 screen 中 `components/` 仅 3 文件 193 行，450+ 处内联样式、~150 个硬编码色值架空了设计令牌；`setScreen` 散落 12 处无路由/返回栈；`index.css:985` 的 `@media(min-width:1100px){#root{max-width:1080px}}` 已成死规则（760 永不触发）；z-index 层级散落两处（60~9500 无统一表）；`ResultScreen.tsx:49` 用了原生 `alert`，与项目自己 `ConfirmDialog.tsx` 里"不用原生弹窗"的注释自相矛盾；爬塔容错阈值 2 与 3 混用（`IntermissionHub:139` vs `BattleEval:103`）。

**可访问性**：全仓 `tabIndex` **0 处**、`role="dialog"`/`aria-modal` **0 处**、Esc 仅 1 处——布阵/装备/筛选/开箱全键盘不可达，弹窗无焦点管理，键盘与读屏用户基本被挡在门外。

**内容侧**：`giant` 体型永不产出却被引擎 4 处引用（死内容）；`TRAIT_VFX` 仅覆盖 7/15 特性；技能文案近复制粘贴（骸骨突袭≈偃月突斩）；**9 处 `[PLACEHOLDER · 待平衡]` 残留**；`story.ts` 仍写"第 30 层胜利即通关"而 `ENDLESS_CAP=500`；教学写 4 个爬塔战略实际只有 3 个且名字不同。

**确定性专项结论**：core 内 `Math.random / Date.now / Math.pow / sin / cos` **0 处命中**，`detmath` 快路使用规范，键序遍历安全 —— **未发现违反确定性的实际调用**。唯一遗留风险：`equipment.ts:94` 的 `eid`、`consumables.ts:48` 的 `cid` 等模块级自增计数器**无 reset 函数**（与已被修过两次的 `uid`/`bId` 同类），目前未进战斗校验和故不破 parity，但后续一旦纳入即复现漂移。
